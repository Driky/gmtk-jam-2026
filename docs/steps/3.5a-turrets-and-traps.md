# Step 3.5a — Turrets & traps

**This file owns no decisions.** It is an execution checklist, like [roadmap.md](../roadmap.md): every
decision below names its owning doc, and the "Doc reconciliation" section lists the owning-doc edit this
step must make **in the same commit** as the code. Never restate a decision here as if this file owned

Siblings: [3.5b](3.5b-ladder-and-climbing.md) · [3.5c](3.5c-chest-and-beacon.md).

## Scope & exit criterion

The first things the player builds that *fight*, plus the pool fix that gates them.

**Exit criterion:** `miner → belt → furnace → belt → ammo press → belt → turret` running *during* a
wave, the turret killing a walker, and a spike trap bleeding one that walks over it.

Nothing about defense exists in code today — `grep -riE "turret|spike|chest|beacon|ladder|climb"` over
`scripts/` returns only forward-referencing comments. This is greenfield on a mature base, and the seams
have been waiting since 3.1.

Two decisions taken with the user that grow this past the roadmap's bullet text:

- **The turret draws power *and* eats ammo**, and ammo is a real tiered item crafted in an **ammo
  press** — pulling that deployable forward from 4.2. It costs no new script
  ([automation.md](../systems/automation.md) §Categories already promises the press is "a `.tscn`, a
  `station_id` and rows in `data/recipe_defs.gd`"), and it makes the chain four machines long, which
  overshoots Day 3's exit criterion rather than just meeting it.
- The turret's projectile is read **off the ammo**, not authored on the turret, so an ammo tier is a
  `.tres` pair and no new table exists.

## 1. Pool sizing 🔴 — `scripts/combat/projectile_pool.gd`

**This gates everything else in the step. Do it first and land it on its own.**

A fixed 32-slot pool steals shots that are still in flight. Every turret is another spawner, so the bug
gets worse the more you build — exactly backwards. The fix is already prescribed in
[player-combat.md](../systems/player-combat.md) §Combat, and the ❗️block at
`projectile_pool.gd:19-26` spells it out.

- `const POOL_SIZE := 32` → `BASE_POOL_SIZE`; add `func pool_size() -> int`. The loops in `_ready`
  (`:39`) and `_take` (`:87-88`) count `_pool.size()`, not the const.
- `var _reserved := 0` — an **instance** var, not a static. `static func reserve(count: int)` /
  `release(count: int)` no-op when `instance == null`, the same inert-without-a-node contract `fire()`
  (`:59`) and `Hud.show_toast` already use.
  - ❗️**Why an instance var:** it dies with the scene reload, so there is no `reset_run()` hook to
    forget. A static counter would survive a restart and hand out capacity for turrets that no longer
    exist — the exact trap `automation.gd:268` documents for the tick registries.
- `_grow_to(BASE_POOL_SIZE + _reserved)` instantiates the delta and appends. **Never shrinks**, so
  `release` only keeps the counter honest for the next `reserve`. Growing mid-wave is safe *because*
  nothing holds a `Projectile` reference across frames.
- Keep the round-robin steal in `_take` as the last-resort backstop.

**Also add an optional `damage_scale := 1.0`** threaded `ProjectilePool.fire` → `Projectile.launch`
(`projectile.gd:65`) → stored → multiplied in `_resolve_contacts` (`projectile.gd:122`). Four lines,
defaulted so `player.gd:340` is untouched. This is how a turret applies
`Progression.get_stat("turret_damage")` — a buff [progression.md](../systems/progression.md) §Skill tree
already names — without duplicating a shared `ProjectileStats` per shot, and spells (4.2) get
`spell_damage` the same way.

⚠️ `tests/combat/test_projectile.gd:219,228` reference `POOL_SIZE`; update them. New tests: reserve
grows the pool · release does not shrink it · a reserved pool no longer steals under the load that used
to saturate it · `damage_scale` scales the hit.

## 2. `Waves.enemies()` — the target query

No shared "find enemies" helper exists. `Waves.debug_poke_nearest()` (`waves.gd:139-151`) and
`Player._enemy_in_swing_range()` (`player.gd:322-329`) each roll their own scan over the `&"enemies"`
group. [tech-design.md](../tech-design.md)'s codebase map assigns "aggro helpers" to `Waves`.

- `func enemies() -> Array[Node]` on `waves.gd` — a thin read of
  `get_tree().get_nodes_in_group(&"enemies")`.
- Refactor `debug_poke_nearest` onto it (12 lines → 2). **Leave `player.gd` and `hud.gd:266` alone** —
  they ask different questions and churning them buys nothing.

**Selection stays pure and static**, so the part that can be wrong in a way a screenshot hides
unit-tests with no world at all — the argument [automation.md](../systems/automation.md) §Power makes
for `PowerGrid` being a solver:

- `static func Turret.pick_target(candidates: Array, from: Vector2, range_px: float) -> Node2D` —
  nearest in range, skipping invalid instances.
- `static func SpikeTrap.victims(candidates: Array, area: Rect2) -> Array[Node2D]`.

❗️[automation.md](../systems/automation.md) §Categories → Defense currently says turrets target
"nearest/**highest-threat** in range". Highest-threat is incoherent for a turret: `ThreatTable` is a
*mob's* private list of who to attack, not a targetability score, and a turret has no threat toward a
mob it has not shot yet. **Nearest in range, full stop** — strike the ambiguity in that doc.

## 3. Ammo press + ammo tiers — data only, no new script

- `scenes/automation/ammo_press.tscn` — the **existing** `CraftingStation` script,
  `station_id = "ammo_press"`, 2×2, non-directional, `support_dirs = 15`, `power_demand = 1.0`, one
  `ColorRect` child named `Visual` (the ghost preview is probed off its **offsets**,
  `deployable.gd:532-546`).
- `data/projectiles/copper_bolt.tres`, `iron_bolt.tres` — `ProjectileStats`; iron hits harder.
- `data/items/copper_ammo.tres`, `iron_ammo.tres` — `ItemStats` with `icon_color` + `projectile`, no
  `place_scene` (not placeable). Keep them **absent from `Materials.LOOT_XP`**: crafted outputs are not
  an XP channel ([progression.md](../systems/progression.md) §XP).
- `data/recipe_defs.gd` — two rows:
  `{station = "ammo_press", inputs = {copper_bar = 1}, output = {id = "copper_ammo", count = 4}, ticks = 20}`
  and the iron equivalent. `accepts_input` then makes the press take bars only, with no change to
  `crafting_station.gd`.
- `data/item_defs.gd` — `const` preloads + `STATS` rows for the press, both ammo ids and the turret.
  That alone earns each one a HUD icon and an F3 give-item row (`item_defs.gd:46-53`).

⚠️ **"One tier per ore tier" ships as copper + iron only.** They are the two ores with a bar recipe
today; `gold` and `magmatite` have no bar, and authoring one is roadmap **4.2** ("Recipes across
tiers"). Their ammo is two more rows in this same table when their bars land. The pattern is set here;
the data entry stays where the roadmap put it.

## 4. Turret — `scripts/automation/turret.gd` + `scenes/automation/turret.tscn`

`class_name Turret extends Deployable`. 1×1, `directional = false` (it auto-targets — a facing arrow
would be a lie), `removal_hits = 2`, `power_demand = 0.5`, `item_id = "turret"`.

✅ **LANDED — read this before the text above.** Two things changed against what this section
originally specified:

- **`support_dirs = 4` (Down), not `SUPPORT_ALL`.** Support differs per turret variant, and a standard
  turret wants a horizontal base under it. This also corrected
  [automation.md](../systems/automation.md) §Deployable base, which used the turret as its example of
  `1` (Up) — a line this doc's reconciliation list originally missed.
- **The reservation is computed per turret from its AUTHORED `ammo_ids`**, because `on_placed()` runs
  before any ammo is loaded, so the `lifetime` named below does not exist yet:
  `ceili(max_lifetime_over_ammo_ids / (fire_ticks × TICK_INTERVAL)) + 1`.
- Shipped values are `max_hp = 50`, `fire_ticks = 5` — the Day-3 stubs of 30/10 made a lone turret lose
  1v1 to a single walker (walker 10 DPS vs turret 5 DPS, both 30 HP), which fails this step's own exit
  criterion. Still stubs; 4.6 owns balance.

- `on_placed()` → `Automation.register_machine(self)` **and** `ProjectilePool.reserve(reserve_shots())`.
  `on_removed()` unregisters and releases. This is the whole reason §1 comes first.
- `on_tick(terrain)` opens with `if not spend_power_tick(): return` — the documented gate, **once per
  tick, from `on_tick` only** (`deployable.gd:392`). A brownout then reads as a slower rate of fire,
  which is the brownout rule working rather than a special case in the turret.
- Cooldown in whole ticks (`fire_ticks`), then
  `pick_target(Waves.enemies(), global_position, range_tiles * TILE)`.
  - ❗️**An idle poll must not burn the cooldown.** The inserter's rule
    ([automation.md](../systems/automation.md) §Categories) for the inserter's reason: a turret whose
    cooldown depends on *when* a mob happened to wander into range feels laggy and makes its DPS
    depend on mob timing.
- Fires through `ProjectilePool.fire(..., faction, self)` using the base's `faction`
  (`deployable.gd:71-74`) — the var 3.1 declared for exactly this and nothing has read yet. Threat
  attribution comes free: `Enemy.take_damage` adds threat to `attacker`, so a turret tanks its own
  aggro, already the designed behaviour ([enemies.md](../systems/enemies.md) §Aggro).
- **Ammo slot** — one `Dictionary`, byte-identical to a conveyor slot and an `Inventory` slot, with
  `accept_item` routing by id against an authored `@export var ammo_ids: PackedStringArray`. This is
  `Generator.accept_item` (`generator.gd:61-74`) verbatim: `extract_item` stays at the base's refusing
  default for the generator's reason (ammo loaded is spent, not stored), and `take_cargo()` hands the
  ammo back on removal.
- **The projectile comes from the ammo, not the turret**: `Items.stats_for(ammo_id).projectile`.
  `ItemStats.projectile` already exists (`item_stats.gd:49`) and is exactly this field, so **no new
  table**. An unknown ammo id fires nothing rather than crashing.
- `is_idle()` → out of ammo. Joins the HUD's idle counter with no type check anywhere — the generator's
  "come and feed me" signal ([ui.md](../systems/ui.md) §HUD).
- The bolt icon over an unpowered/browned-out turret is **free**: `power_overlay.gd:204` walks
  `Automation.machines()` and keys on `power_demand > 0`.
- `slot_overlay.gd` — add an `as Turret` block beside the `as Miner` (`:120`) and
  `as CraftingStation` (`:132`) ones: ammo stack, cooldown, target-or-none. The overlay reads machines
  with `as` casts **by design**; do not push a readout API onto the base to keep one debug node tidy.

## 5. Spike trap — `scripts/automation/spike_trap.gd`

1×1, `power_demand = 0` — [automation.md](../systems/automation.md) §Categories authors Defense's trap
as explicitly unpowered — and `support_dirs = 4`.

- ❗️**`4` is Down**, i.e. a solid tile *below* it: `SUPPORT_OFFSETS[2]` is `DOWN` and the flags are
  `1=Up, 2=Right, 4=Down, 8=Left` (`deployable.gd:12-18`). That comment warns inverting Up/Down
  "produces a game that mostly works with no error anywhere", which is why there is a dedicated
  orientation test — write one here too.
- Registers as a machine so it gets `on_tick` free. `spend_power_tick()` is a no-op returning true at
  demand 0; **call it anyway**, so a powered variant later is data rather than a code change.
- One **global** `damage_ticks` cooldown hitting everything standing on it, not a per-victim table: a
  spike pit with four mobs in it is the case that matters, and a per-victim dict is a second place for
  state to live and to serialize at 4.3.
- **Enemies only.** A trap that hurts the player is a death with no readable cause, and nothing on
  screen ties a hit to a tile. Neither owning doc specifies it; this takes the safe reading, so record
  it in [automation.md](../systems/automation.md).
- Damage via `Enemy.take_damage(amount, self)`, so a trap draws threat and mobs stop to chew it — the
  torch precedent ([terrain.md](../systems/terrain.md) §Lighting), and why a trap has HP worth
  authoring.

## ⚠️ Open hole, unrelated to this step but do not lose it

Recorded here because 3.5a is the first step to be written; [3.5b](3.5b-ladder-and-climbing.md) links
back to it. **Nothing in 3.5 closes this.**

[enemies.md](../systems/enemies.md) locks "capabilities are speed, digging is correctness". That is true
only against **solid** obstructions. A **vertical air gap is not diggable**: a walker facing air above
resolves to `Action.NONE` (`enemy_locomotion.gd:48-54`), the direct-to-Core fallback returns NONE too
(`enemy.gd:126-131`), and the stuck watchdog has nothing to escape to — you cannot chew air. Meanwhile
the flow field *believes* the route works, because an up-move through air is legal whenever either end
has any solid neighbour (`flow_field.gd:168`) — the wall-climber over-connectivity whose error
[enemies.md](../systems/enemies.md) §Pathfinding claims "the dig fallback absorbs". **It does not absorb
this one.**

Walls do **not** seal a base: `wall` is `min_tool_tier = 1, hardness = 3.0`, so a solid cell costs
`1 + hardness/dig_power = 4.0` and a shell is chewed. But a Core on a floating platform, a moat with an
overhang, or any lip a walker must ascend soft-locks ground mobs today.

The designed answer is [enemies.md](../systems/enemies.md) §Wave composition's fortification score
skewing spawns toward crawlers (`climb_speed > 0`) and flyers (air field) — roadmap **4.1**, with
✂️9's pre-authorized fallback being fixed unlock waves. Mob-usable ladders (3.5b) do **not** help: a mob
can only climb a ladder the player built. Two cheap candidates for 4.1: make the ascending-through-air
edge require a capability the reference mob actually has, and give the stuck watchdog a lateral-search
escape rather than only direct-dig.
