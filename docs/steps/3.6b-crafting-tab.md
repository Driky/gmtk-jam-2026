# Step 3.6b — Crafting tab

**This file owns no decisions.** It is an execution checklist, like [roadmap.md](../roadmap.md): every
decision below names its owning doc, and the "Doc reconciliation" section lists the owning-doc edit this
step must make **in the same commit** as the code. Never restate a decision here as if this file owned
it ([tech-design.md](../tech-design.md)).

Sibling: [3.6a](3.6a-window-and-inventory.md), which must land first — this tab lives *inside* that
window and uses its `ItemSlot` widget and its held-stack model.

## Scope & exit criterion

The crafting tab, the recipes it can actually run, and the crafting-range query every cost check draws
from ([progression.md](../systems/progression.md) §Crafting range, [ui.md](../systems/ui.md)
§Character screen).

**Exit criterion:** with ore in a chest beside you, craft a miner by hand from the crafting tab.

❗️**This is the step that makes the game obtainable.** `RecipeDefs.RECIPES` holds four rows today, all
`station = "furnace"` or `"ammo_press"` — **nothing the player can craft**. `main.gd`'s `STARTING_KIT` is
a pickaxe and 20 torches, so every deployable in the game reaches the player only through the F3
give-item dropdown or the factory rig, and an exported build has no console
([ui.md](../systems/ui.md) §Build factory rig says so as the reason that rig exists). A crafting tab over
the existing four rows would be a tab with nothing to press.

## 1. `data/recipe_defs.gd` — three fields and the hand rows

The `station = "hand"` convention and the two new columns belong to
[progression.md](../systems/progression.md) §Recipe tiers. Here:

- **`category` and `unlocked_by := ""` on every existing row as well as the new ones.** `""` means always
  available, so 3.7 fills the column in with no consumer change — the argument this file already makes at
  `recipe_defs.gd:16-19` for `inputs` being a map from day one. Widening a shipped table's shape later is
  a rewrite of every consumer.
- **Hand rows** for the deployables: torch, ladder, chest, beacon, conveyor, inserter, miner, furnace,
  generator, relay, spike trap, turret, ammo press. `ticks = 0` — the hand path does not tick.
- ❗️**Hand rows are invisible to a `CraftingStation` only because no scene authors
  `station_id = "hand"`.** `accepts_input` (`recipe_defs.gd:56-60`) and `for_station` (`:42-47`) filter on
  that string alone, and `CraftingStation.accept_item` routes by id through the former — so a furnace
  would happily eat a hand recipe's inputs the day someone authors that `station_id`. Pin it with a test
  rather than leaving it to luck.
- Recipe **display names come from `Hud.item_name(recipe.output.id)`** (`hud.gd:329`). Add no name field:
  it would be a second place for a name to drift from `ItemStats.display_name`, which is the exact reason
  that static exists.
- ⚠️ Balance is 4.2/4.6. Ore counts here are placeholders whose only job is to make the chain
  *mine → smelt → craft* reachable.

## 2. `Items.gather_available` / `containers_near` / `consume_available` — `scripts/items/items.gd`

`items.gd`'s own header already claims crafting-range queries as this file's job, and
[progression.md](../systems/progression.md) §Crafting range assigns the query here. The discovery
decision (a `&"container"` group on the scene root) is
[automation.md](../systems/automation.md) §Categories → Utility's. Execution:

- Add `groups=["container"]` to `scenes/automation/chest.tscn`'s **root node** — one line of scene data,
  no code, exactly as `respawn_beacon.tscn:5` declares its group.
- ⚠️ **Iterate the group untyped.** `for node in get_tree().get_nodes_in_group(&"container")` — a typed
  loop variable fails on the *assignment* of a freed instance before any `is_instance_valid` guard in the
  body can run, which is what `tools/check_freed_safety.sh` blocks and what `Turret.pick_target` already
  pays for.
- `gather_available(player_pos) -> Dictionary` returns flat `{item_id: total_count}`. Flat counts rather
  than a list of `Inventory`s: every consumer asks "do I have ≥ N of `id`".
- Radius ~12 tiles. ⚠️ `Player.REACH_RADIUS_PX` (4.5 tiles, `player.gd:30`) is the only precedent and is
  far too small — you would have to stand on the chest.
- ❗️**`consume_available(player_pos, inputs) -> bool` is the half most likely to ship broken.** The tally
  is a flattened copy and can remove nothing; a naive per-id removal loop that runs short halfway eats the
  first inputs and produces nothing. Two-phase — verify the **whole** cost, then remove — and it lives
  beside `gather_available` because the two must share the same discovery *and* the same order.

## 3. The crafting tab — `scripts/ui/character_screen.gd` (+ its scene)

Category tabs, unlock filtering and the greyed/missing-input presentation are
[ui.md](../systems/ui.md) §Character screen's. Execution notes:

- Rows are built once in `_ready` with the rest of the window ([3.6a](3.6a-window-and-inventory.md) §6),
  not on open — the same browser-hitch argument.
- `unlocked_by == ""` is the whole of unlock filtering until 3.7; write the branch now so 3.7 is data.
- Crafting: `consume_available` → `player_inventory.add_item` → ⚠️ **leftover to the floor, never
  deleted** — `add_item` returns what did not fit (`inventory.gd:64`), and the loot bag's contract is
  that nothing is silently deleted ([player-combat.md](../systems/player-combat.md) §Death & respawn).
- ⚠️ **An invisible radius is a bug report.** A greyed row with no explanation reads as broken, so the tab
  shows how many containers are in range beside the list.
- ⚠️ The search box ([ui.md](../systems/ui.md) §Character screen, "if time allows") is why
  [3.6a](3.6a-window-and-inventory.md) §6 insists the shortcuts live in `_unhandled_input` — a `LineEdit`
  must be able to receive the letters `I` and `C`.

## Verification

- **No new `class_name` script here**, so no class-cache pass is needed unless §3 grows one. Format and
  check LSP diagnostics as usual; `tools/check_freed_safety.sh` runs in `pre-commit` and §2's group loop
  is the site it targets.
- **Unit tests**, one per plausible-wrong-answer:
  - `test_recipe_defs`: every row carries all six keys · **no `CraftingStation` scene authors
    `station_id = "hand"`** · `for_station("hand")` is non-empty · every hand-recipe output resolves
    through `ItemDefs.stats_for` to something with a `place_scene`.
  - `test_items`: the tally sums the player inventory plus in-range containers · **excludes an
    out-of-range one** · **excludes equipment** · consume is all-or-nothing (short by one input ⇒ nothing
    removed) · consume drains the player inventory before any container · **a freed node left in the
    group is skipped**, which is the case that drives the untyped loop.
- **By hand:** F3 → give ore → open `C` → confirm the miner row is craftable and the rest are greyed with
  the missing input highlighted · craft it and place it · put the ore in a chest instead, stand next to
  it, and confirm the same row is still craftable · walk away and confirm it greys · craft with a full
  inventory and confirm the output lands on the floor rather than vanishing.
- **In a browser:** start a fresh run and build a working `miner → furnace` chain **without touching F3**
  — that is the whole point of this step, and it is not proven anywhere else.
