## Scope & exit criterion

The window, the way items move inside it, and everything that hangs off the inventory tab
([ui.md](../systems/ui.md) §Character screen).

**Exit criterion:** open the screen with `I`, move a stack from slot 27 into the hotbar, wear a helmet
and watch a walker hit for less, press `E` on a chest and shift-click your ore into it.

Three things make this worth doing before the crafting tab:

- **Slots 10–39 are unreachable.** `Inventory` is 40 slots (`inventory.gd:13`); the HUD renders 10.
  `Hud._on_slot_changed` (`hud.gd:484-486`) early-returns above `HOTBAR_SIZE`, and a death drops
  `take_range(KEPT_SLOTS, SLOT_COUNT)` into a loot bag (`player.gd:255`) that hands items straight back
  into slots the player cannot see. `scripts/game/main.gd`'s `STARTING_KIT` docstring says so out loud.
- **The chest was built half-finished on purpose.** `Chest.storage()` exists as a seam with no reader,
  and [3.5c](3.5c-chest-and-beacon.md#L59) defers the panel here by name: *"there is no `interact` input
  action yet… 3.6 adds the view, not the function."*
- **Nothing enforces "a screen is open".** `DebugMenu.is_open` is read at exactly one site
  (`player.gd:161`) and gates only `mine`/`place`. This step is where that becomes a shared rule rather
  than a second copy of one line.

⚠️ **Cut line ✂️8 is irrelevant here; ✂️7 is not fired.** Its wording ("Equipment panel → tool/weapon
slots only") is rewritten rather than fired — see [plan.md](../plan.md) §Cut lines.

## 1. `scripts/ui/item_slot.gd` — extract the slot widget FIRST

`Hud._make_slot` (`hud.gd:518-549`) builds a `ColorRect` + `TextureRect` + two `Label`s and appends to
three parallel arrays (`_slot_bgs`/`_slot_icons`/`_slot_counts`, `hud.gd:69-71`). **This screen needs 68
of them** — 40 inventory + 20 chest + 8 equipment. Copy-pasting is three more parallel-array sets and a
second home for the icon and count rules to drift from.

`class_name ItemSlot extends ColorRect`, with `set_stack(Dictionary)`, `set_selected(bool)` and
`signal slot_pressed(index: int, button_index: int, shift: bool)`. Constants (`SLOT_SIZE`, `SLOT_MARGIN`,
`NORMAL_BG`, `SELECTED_BG`, `ICON_SIZE`) move here from `hud.gd:12-17`.

- Reuses the **static** `Hud.icon_for(id)` (`hud.gd:296`, cached in `_icon_cache`) and
  `Hud.item_name(id)` (`hud.gd:329`) rather than resolving names or textures itself. Both are inert
  without a HUD in the tree, so this widget unit-tests headless.
- The optional key label (`"1"`–`"0"`) stays an opt-in, so a grid slot and a hotbar slot are one widget.
- **Refactor the HUD hotbar onto it in this same commit.** `tests/ui/test_hud.gd` already asserts against
  `_slot_counts[i].text` and the selected-slot colour, so the refactor is verified by tests that already
  exist — the cheapest possible proof that the extraction is faithful.

## 2. `scripts/items/inventory.gd` — a total, non-aliasing mutation API

❗️**`get_slot` hands back the LIVE dict** (`inventory.gd:96-97`) and every mutator mutates it in place:
`add_item` does `slot.count += moved` (`:52`), `remove_from_slot` does `slot.count -= removed` (`:73`)
then rebinds `_slots[index] = { }` (`:75`). A UI that parks `get_slot(i)` on the cursor gets **free items
every time a pickup magnets in** — `pickup.gd` and `loot_bag.gd` both route through `add_item` and grow
that same dict. This fires during ordinary play, not in a corner case. `take_range` (`:89`) is the only
method that already does the right thing (`.duplicate()` before clearing); it is the pattern to copy.

```gdscript
func take_slot(index: int) -> Dictionary                       # whole stack, detached; {} when empty
func take_from_slot(index: int, count: int) -> Dictionary      # up to `count`, detached
func put_in_slot(index: int, stack: Dictionary) -> Dictionary  # returns what the CALLER still holds
func add_item_in_range(id: String, count: int, from: int, to: int) -> int
```

- **The invariant, and what every test pins:** each call is **total** — the sum of `count` over (all
  slots + the held stack) is unchanged. `put_in_slot` returning the residue (the overflow on a merge, the
  displaced stack on a swap, `{}` when it all went in) is what makes it so.
- ❗️**Do not add a `set_slot(index, stack)`.** It cannot be total, and it is the one signature that makes
  every dupe bug above reachable again.
- ❗️**Mutate `_slots` completely, THEN emit.** `slot_changed` fires synchronously into three listeners —
  `Hud._on_slot_changed` (`hud.gd:484`), `MiningCursor._on_slot_changed` (`mining_cursor.gd:133`) and
  `Player._on_slot_changed` (`player.gd:725`), which **frees and re-instantiates the swing hitbox** via
  `_equip`. Emitting mid-swap shows them a world where the item exists twice or not at all.
- ⚠️ `add_item` starts at slot 0 (`:45`), so without `add_item_in_range` a shift-click *out of* the
  hotbar merges straight back into a hotbar stack. Refactor `add_item` to
  `return add_item_in_range(id, count, 0, _slots.size())`, so there is exactly one stacking implementation.
- ⚠️ The RMB half-split is `ceili(count / 2.0)`. Integer division makes a click on a stack of 1 a silent
  no-op.

## 3. `scripts/items/equipment.gd` + two `ItemStats` fields

`class_name Equipment extends RefCounted`, `enum Slot { HELMET, CHEST, LEGS, FEET, BACK, RING_1, RING_2,
NECKLACE }`, `signal slot_changed(slot: int)` — deliberately the same shape as `Inventory.slot_changed`,
so §1's one widget binds either model. API: `get_item(slot)`, `equip(slot, id)` (returns the displaced
id, `""` if none), `unequip(slot)`, `armor_total()`, `static slot_accepts(slot, id)`.

`scripts/items/item_stats.gd` grows `@export var equip_slot := EquipSlot.NONE` and
`@export var armor := 0.0` under an `@export_group("Equipment")`.

- ❗️**The legacy case solves itself, and that is the reason the field goes on `ItemStats`.**
  `ItemDefs.stats_for` never returns null (`item_defs.gd:119-124`), and both fallbacks (`BARE_HAND`,
  `BLOCK_DEFAULT`) default to `NONE` — so all 19 authored items and every material in `Materials.ORDER`
  are non-equippable with **zero data migration**. Pin it with a test: it also catches a future `.tres`
  authored with a stray slot.
- ❗️**Not an `Inventory` with 8 slots.** `add_item` (`:43`) would cheerfully put a helmet in the feet
  slot from any auto-fill path, and `count_of`/`take_range` would then treat worn gear as ordinary cargo.
- `RING` is **one** authored enum value on the item; `slot_accepts` answers true for both ring slots.
  `ItemStats` must not know there are two.
- `Items.equipment := Equipment.new()` beside `player_inventory` (`items.gd:6`), ❗️plus **one new line in
  `Items.reset_run()`** (`:25-26`), which today only replaces the inventory. Forget it and you keep your
  armor across runs — invisible until run two.
- Ships **~3 sample pieces** (`.tres` + `ItemDefs.STATS` rows) so the panel demonstrably does something;
  an `ItemDefs.STATS` entry earns each an F3 give-item row for free (`debug_menu.gd:424-434`). The full
  set is 4.2 content.

## 5. `scripts/ui/ui_state.gd` — one predicate, not a growing OR

Suppression today is one read at `player.gd:161`, sitting **after** `_move(delta)` (`:156`) — so with F3
open you can still walk and jump, and only `mine`/`place` are gated. Three screens would mean three ORs
at every polling site. The rule and the two-predicate split belong to [ui.md](../systems/ui.md) §Pause;
the shape here is a `class_name`-only statics script (the `Perf` / `RecipeDefs` precedent — no autoload
slot, so [tech-design.md](../tech-design.md)'s fixed map is untouched):

```gdscript
static func blocks_gameplay_actions() -> bool   # DebugMenu.is_open or CharacterScreen.is_open
static func blocks_movement() -> bool           # CharacterScreen.is_open only
```

❗️**Blocking movement is not a guard at the top of `_step`.** Skipping `_move` skips the gravity block
*and* `move_and_slide()`, so the player freezes in mid-air. It has to zero the **input reads**, at five
sites in `player.gd`:

- `_move`: `Input.get_axis("move_left", "move_right")` (`:447`) and `Input.is_action_just_pressed("jump")` (`:462`)
- `_try_climb`: the `get_axis("move_up", "move_down")` read (`:510`), the `_climb_locked` fresh-press
  check (`:515`), and the climb branch's own jump-buffer decay (`:532`)

Wrap them in `_move_axis()` / `_jump_pressed()` / `_climb_axis()`. ❗️Skipping this ships **the Space
bug**: `jump` is Space, a focused `Button` consumes `ui_accept`, so pressing Space over a button in the
window activates it *and* jumps.

**Two latent bugs get their one-line gate in this same commit**, because the screen makes both visible:

- `Hud._refresh_inspector` runs unconditionally in `_process` (`hud.gd:167-175`) and its `_hovered_slot`
  (`:256`) hit-tests only the ten hotbar rects. With the screen open, hovering your inventory grid runs a
  `Terrain.get_entity` probe **plus a full enemies-group loop** (`_enemy_at`, `:265-272`) every frame and
  names the tile *behind* the window — on layer 0, so it draws underneath, invisible and still costing.
- `MiningCursor` (`scripts/player/mining_cursor.gd`) polls `_player.target_tile()` and redraws every frame (`mining_cursor.gd:108-114`) with
  no open-screen check, sliding a green/red placement ghost around the world while you sort your bag.

## 6. `scripts/ui/character_screen.gd` + `scenes/ui/character_screen.tscn` — the shell

`class_name CharacterScreen extends CanvasLayer`. Layer, the no-dim rule and the tab shortcuts are
[ui.md](../systems/ui.md) §Character screen's; the mechanics here:

- `static var is_open` mirroring `DebugMenu.is_open` (`scripts/debug/debug_menu.gd:18`) **including the `_exit_tree`
  clear** — "never leave the flag set for the next scene" (`:214`). Plus `static var _instance` set in
  `_ready` / cleared in `_exit_tree`, the `Hud.show_toast` / `ProjectilePool.fire` idiom (`hud.gd:36-46`),
  so §9's `open_container` needs no node path and is **inert with no screen in the tree** — headless
  tests are unaffected.
- `process_mode = PROCESS_MODE_ALWAYS` (`debug_menu.gd:208`) so Esc still closes it under the paused
  game-over screen, **plus** a `Game.state_changed` handler that closes it on `GAME_OVER` and a guard so
  it cannot be *opened* there. Without both it draws under a screen it outranks on nothing.
- Injectable `inventory` / `equipment` properties defaulting to the autoloads in `_ready` — the `Hud`
  seam (`hud.gd:49-60`), and the only way a suite drives this without the live `Items`.
- ⚠️ `toggle_inventory` / `toggle_crafting` / `toggle_skill_tree` / `pause` in **`_unhandled_input`**,
  never `_input`, or 3.6b's search box can never receive the letters `I` or `C`. Esc closes and calls
  `get_viewport().set_input_as_handled()`; 4.5's pause menu takes the else-branch. Leave a marker saying
  so — without that call the precedence between the two is scene-order dependent.
- ⚠️ **Build all 68 slot widgets once in `_ready`**, never on open and never on tab switch. ~272 Controls
  instantiated on a keypress is a visible hitch in a browser, and `visible` costs nothing.
- ⚠️ **No `_process`.** Signal-driven like the HUD's bars. The cursor-following held-stack ghost is the
  one exception and rides `_input` on `InputEventMouseMotion`, so it costs nothing while the mouse is still.
- ⚠️ **Do not hide the OS cursor** — that requires pointer lock on web. Offset a Control from the pointer
  exactly as `_refresh_inspector` positions the inspect label (`hud.gd:212-218`), **including its
  bottom-edge flip**, which you want here for the same reason: a clamped ghost lands on the slot it is
  hovering.

Instanced in `scenes/main.tscn` beside `%HUD` with `unique_name_in_owner`, shown by `scripts/game/main.gd::_finish_generation()`
alongside the HUD toggle (the same ownership moment).

## 7. Inventory tab & the held stack

40 slots, slots 0–9 laid out as the hotbar row. Interaction model (LMB pick/put/swap, RMB one-or-half,
shift-click quick-move) is [ui.md](../systems/ui.md) §Character screen's, including where the held stack
lives and why.

❗️**Every exit path calls one `_return_held()`, or the cursor stack is silently deleted.** Four of them:
the window closed (`I`/`C`/`K`/Esc/tab close), `died`, the open container destroyed (§9), and
`GAME_OVER`. Return goes to `Items.player_inventory.add_item`, and the leftover becomes a world pickup
through the `pickup_spawner` group (`pickup_spawner.gd:23`) carrying `grants_xp = false` — the same sink
and the same flag as `Deployable.pop_to_pickup` (`deployable.gd:335`).

❗️**Death is a live exploit as designed, and it is not obvious from reading `_die`.** `_die()` calls
`_drop_loot_bag()` — which is `take_range(KEPT_SLOTS, Inventory.SLOT_COUNT)` (`player.gd:255`) — and only
*then* emits `died` (`:248`). A stack held on the cursor is in **neither** the inventory nor the bag, so
it survives death untouched: open the screen, pick up your 99 magmatite, die, keep it while everything
else drops. Fix it **without reordering `_die`** — on `died`, the screen drops the held stack as a world
pickup at the player position. Order-independent, and it reuses the one drop path.
[player-combat.md](../systems/player-combat.md) §Death & respawn records the fact.

Shift-click is **offer first, consume second** — `var moved := dst.add_item_in_range(...)` **then**
`src.remove_from_slot(i, moved)`. `Player.hand_feed` (`player.gd:659-663`) already argues why: the other
order is one full-destination away from eating the item.

⚠️ `Inventory.selected_slot` clamps to `HOTBAR_SIZE - 1` (`inventory.gd:20-26`), so "selecting" grid slot
23 silently becomes 9. **"Hotbar assignment" means moving items into slots 0–9, not moving the
selection** — build no selection affordance over the grid.

## 8. Equipment panel & stats readout

Eight `ItemSlot`s bound to `Items.equipment`. A wrong-type drop is **refused and the cursor keeps its
stack** — nothing is consumed on a rejected click, the `accept_item` bargain. A stack of 5 helmets equips
**one** and returns 4 to the cursor; a displaced piece goes to `player_inventory.add_item` with leftover
to the floor. Same conservation invariant as §2, no new exit for an item.

Readout: `player.current_hp` + `Progression.get_stat("max_hp")`, the same pair for mana,
`Progression.get_stat("move_speed")`, and `Equipment.armor_total()`. ⚠️ Move speed is **not** a player
member — it is read from `Progression` every frame in `_move` (`player.gd:447`).

## 9. `interact` + the container view

A new `interact` action on **`E`** in `project.godot` (26 actions today, none is `interact`; `E` is free).
The binding is [ui.md](../systems/ui.md) §Bindings'.

**The handler lives on the Player**, which already owns `target_tile()` (`:745`), `in_reach()` (`:749`)
and the `Terrain.get_entity(cell) as Deployable` idiom (`_hit_deployable`, `:359-371`). The screen owns no
cursor→cell conversion and should not learn one. It fires from `_unhandled_input` beside
`rotate_placement` (`:426`), and reaches the screen through the static `CharacterScreen.open_container(node)`.

- ❗️**Duck-typed on `has_method(&"storage")`, not `as Chest`** — the "`as Deployable`, not a group check"
  precedent (`player.gd:356-358`), so 4.x's next container needs no edit here.
- ⚠️ `rotate_placement` and the hotbar keys at `player.gd:425-432` are **ungated** by `DebugMenu.is_open`
  while `mine`/`place` are gated. Pick one of the two existing behaviours for `interact` rather than
  introducing a third at the same call site.

**The container destroyed while its panel is open.** All three removal paths converge on `pop_to_pickup`
(`deployable.gd:317-335`), whose order is `remove_entity` per cell → **`on_removed()`** → `take_cargo()`
→ `queue_free()`. That order is a gift: a `Chest.on_removed()` override calling the static
`CharacterScreen.close_container(self)` runs **before** the chest empties and **before** it is freed, so
the panel closes and `_return_held()` puts the cursor stack into the **player's** inventory rather than
into a dying container. `deployable.gd` needs no change at all.

- ⚠️ **Bind the container's `slot_changed` with a named method, not a lambda.** A fresh `Callable` per
  open is undetectable as a duplicate, so opening the same chest twice repaints every slot twice, forever.
  `disconnect` on close, guarded by `is_connected`.
- ⚠️ **Never annotate the stored chest reference in a loop and never key a `Dictionary[Chest, X]`** —
  both are `tools/check_freed_safety.sh` failures ([tech-design.md](../tech-design.md) / CLAUDE.md).
  `is_instance_valid` on every read.

## As built (3.6a, shipped)

This file was written before the step ran. Everything above held except the six
points below; each is recorded in the doc that owns it, and none of them is
restated here as a decision.

- **Commit order is §1 §2 §3 §4 §6 §5 §7 §8 §9**, not the order listed above. `UiState`
  names `CharacterScreen.is_open`, which does not parse until that class exists, so
  the shell has to land first. Nothing else depends on the order.
- **`Chest.on_removed` reaches the screen by the group `&"character_screen"`**, not
  by the static named in §9. Naming `CharacterScreen` there closes a dependency
  cycle through a **resource** — `chest.gd → CharacterScreen → ItemSlot → Hud →
  ItemDefs → chest.tres`'s `place_scene` `→ chest.tscn → chest.gd` — and Godot
  cannot resolve `ItemDefs.STATS` inside it, so the HUD stops compiling at boot.
  It constrains every deployable, so it is recorded in
  [automation.md](../systems/automation.md) §Categories → Utility.
- **`main.gd` binds the player to the screen rather than showing it.** The screen
  owns its own visibility and starts closed; what that moment hands over is the
  player the stats readout and the death drop need — the `Hud.bind_player` seam.
  Until it lands, `can_open()` is false, so `I` cannot draw over the loading bar.
- **Eight authored pieces, seven `.tres`** (§3 said "~3 samples"). ⚠️ They sum to
  15 but a fully-worn set is **16**: `copper_ring` fills both ring slots.
- **`ICON_SIZE` stayed on `Hud`** rather than moving to `ItemSlot` with the layout
  constants (§1): `icon_for` is its only reader, and moving it would leave the HUD
  reaching back into the class it constructs.
- **`Equipment.equip` has no "already wearing that" shortcut.** With one piece
  authored per slot, identical is the only displacement that exists, and a call
  that silently did nothing while returning `""` is indistinguishable from an empty
  slot — the screen would consume an item from the cursor for a swap that never
  happened.

⚠️ The step doc's claim that the HUD is on **layer 0** was wrong throughout:
`hud.tscn` sets no `layer` and takes Godot's default of **1**. Layer 5 for this
screen was still correct. Fixed in [ui.md](../systems/ui.md) and `debug_menu.gd`;
no actual layer number changed.
