# Step 3.7 — Skill tree system

**This file owns no decisions.** It is an execution checklist, like [roadmap.md](../roadmap.md): every
decision below names its owning doc, and the "Doc reconciliation" section lists the owning-doc edit this
step must make **in the same commit** as the code. Never restate a decision here as if this file owned
it ([tech-design.md](../tech-design.md)).

Predecessors: [3.6a](3.6a-window-and-inventory.md) (the window this tab lives in, its `ItemSlot` widget,
its no-`_process` rule) and [3.6b](3.6b-crafting-tab.md) (the `unlocked_by` column this step fills, the
`gather_available`/`consume_available` pair a `resource_cost` pays through, and the repaint `Timer` this
tab reuses). Both have landed.

## Scope & exit criterion

The `SkillNode` Resource, the run state that spends points into it, the three buff seams that do not
exist yet, and the tree tab ([progression.md](../systems/progression.md) §Skill tree,
[ui.md](../systems/ui.md) §Character screen).

**Exit criterion, in a browser, with no console:** start a fresh run, dig until level 2, spend the point
on *Logistics I*, and craft a conveyor that was not in the crafting list a minute earlier. Then take
*Armaments* and watch a turret's damage go up.

❗️**This step decides what a new run can build**, which is a bigger change than the tab suggests. Today
all 17 recipe rows are `unlocked_by = ""` and a fresh run can hand-craft every deployable in the game.
After §6 it can craft **a pickaxe, a ladder and torches** — everything else is behind a point. The whole
of §6 is therefore load-bearing on *obtainability*, the property [3.6b](3.6b-crafting-tab.md) exists to
establish, and it is pinned by tests rather than by playing it once.

## 0. Four contradictions in the owning docs, to resolve here

Recorded up front because each one changes what §1–§7 build, and each needs a strike in its owning doc
rather than a workaround in code.

1. ❗️**`unlock_recipes[]` and `unlocked_by` are the same edge stored twice.**
   [progression.md](../systems/progression.md) §Skill tree gives the node an `unlock_recipes[]`;
   §Recipe tiers gives every recipe an `unlocked_by`. Two writable copies of one fact, free to drift the
   first time a recipe moves branch. **`unlocked_by` on the recipe row wins**: it shipped at 3.6b, the
   crafting tab already filters on it, and a recipe has exactly one gate while a node has many
   recipes. `SkillNode` carries **no** `unlock_recipes`; the tab asks
   `RecipeDefs.unlocked_by(node_id) -> Array[Dictionary]`, a third query beside `for_station` and
   `categories_for_station`, so the *order* stays a property of the table as those two already are.
2. ❗️**Three of the five named buffs have no consumer.** `mining_speed` and `turret_damage` are wired
   (`item_stats.gd:78`, `turret.gd:235`); `crafting_speed`, `crafting_yield` and `resource_yield` are
   read by nothing at all. §3–§4 build all three seams. Without it a node claiming `+10% crafting yield`
   is a button that does nothing, which is worse than a tree with fewer nodes.
3. ❗️**A `max_hp` multiplier double-dips through the player's level-up cache.** `_on_leveled_up`
   (`player.gd:220-226`) raises `current_hp` by `max_hp - _last_max_hp` and *only then* refreshes
   `_last_max_hp`. A node that raises the ceiling outside that path leaves the cache stale, so the next
   level-up grants the level's delta **plus the node's**, and the node's own grant never lands as
   current HP. §2 gives `Progression` a `node_unlocked` signal and the player absorbs it through the
   same code (§5) — the alternative is forbidding max-stat nodes, which throws away the one node that
   proves the multiplier composes with `_PER_LEVEL`.
4. ⚠️ **`Items.consume_available` refuses an empty cost** ([progression.md](../systems/progression.md)
   §Crafting range: "an empty cost is refused rather than trivially granted"). Nine of the thirteen
   nodes cost points only. Calling it unconditionally would make **every point-only node unbuyable**;
   the call is guarded on a non-empty `resource_cost`.

## 1. `SkillNode` + the registry — `scripts/progression/skill_node.gd`, `data/skill_defs.gd`

The Resource shape is [progression.md](../systems/progression.md) §Skill tree's. Execution:

- `class_name SkillNode extends Resource`, with `@export` for `id`, `display_name`, `description`,
  `prerequisites: PackedStringArray`, `point_cost := 1`, `resource_cost: Dictionary` (`{item_id: count}`,
  the same shape as a recipe's `inputs`), `max_level := 1`, `stat_name := ""`, `stat_per_level := 0.0`,
  and `position: Vector2` — hand-placed, stored in the Resource, exactly as the owning doc locks.
- `data/skill_defs.gd` is `class_name SkillDefs`, a static-and-pure registry **mirroring
  `data/item_defs.gd` and `data/recipe_defs.gd`**: `const` preloads, a `NODES` dictionary, `node_for(id)`,
  and `all() -> Array[SkillNode]` in authored order (the tab draws in that order, so it is a property of
  this file, not of the UI).
- ⚠️ **`id` is stored on the Resource *and* used as the dictionary key.** `ItemDefs` has the same latent
  duplication and no test; pin it here — a `.tres` whose `id` disagrees with its key resolves through one
  path and not the other.
- `.tres` files under `data/skills/`. No `place_scene`, no scene reference of any kind, so this registry
  closes none of the resource cycles [3.6a](3.6a-window-and-inventory.md) paid for.
- A node that only unlocks recipes carries `stat_name = ""` and `max_level = 1`; a buff node unlocks no
  recipes. Nothing forbids both — the table just has no example.

### The roster (13 nodes, three branches)

Content, so it is the scope lever ✂️2 in [plan.md](../plan.md) points at: **the Industry and Defense
branches carry every recipe unlock and are what the exit criterion needs**; the buff-only leaves are what
gets pruned if Day 3 runs out.

| id | Branch | Prereq | Cost | Effect |
| --- | --- | --- | --- | --- |
| `storage` | Industry | — | 1 | unlocks chest |
| `logistics_i` | Industry | — | 1 | unlocks conveyor, inserter |
| `power_grid` | Industry | `logistics_i` | 1 | unlocks generator, relay |
| `mechanization` | Industry | `power_grid` | 1 | unlocks miner, furnace |
| `rich_veins` | Industry | `mechanization` | 1 ×3 | `resource_yield` +10%/lvl |
| `efficient_assembly` | Industry | `mechanization` | 1 + `copper_bar ×4` | `crafting_yield` +10%/lvl (×3) |
| `mass_production` | Industry | `mechanization` | 1 ×3 | `crafting_speed` +15%/lvl |
| `traps` | Defense | — | 1 | unlocks spike trap |
| `emplacements` | Defense | `traps` | 1 + `iron ×10` | unlocks turret, ammo press |
| `armaments` | Defense | `emplacements` | 1 ×3 | `turret_damage` +15%/lvl |
| `prospecting` | Excavation | — | 1 ×3 | `mining_speed` +10%/lvl |
| `deep_delving` | Excavation | `prospecting` | 1 | unlocks respawn beacon |
| `conditioning` | Excavation | — | 1 ×2 | `max_hp` +10%/lvl |

- ❗️**The five roots (`storage`, `logistics_i`, `traps`, `prospecting`, `conditioning`) cost one point
  and NO resources**, and that is not a balance number: a level-2 player has exactly one point and
  whatever ore they dug by hand, so a root priced in `copper_bar` would be the same deadlock the
  bootstrap-recipe rule already forbids one layer down
  ([progression.md](../systems/progression.md) §Recipe tiers). Pinned by a test, like that rule is.
- ❗️**`power_grid` comes BEFORE `mechanization`**, which is the tree restating a rule the recipe table
  already keeps: the miner and the furnace both carry `power_demand = 1.0`, so unlocking them first hands
  the player two machines that cannot run and no way to power them. Same argument that prices the
  generator in mined materials only (ibid.). Pinned by a test.
- ❗️**Every yield node sits behind `mechanization`**, and that is not flavour: both yield buffs live on
  MACHINES (§3), so a `rich_veins` bought before you own a miner is a point spent on nothing — a trap
  purchase the tree's shape has to make impossible. Pinned by a test.
- **The respawn beacon is on Excavation, not Defense.** It is what you plant when you are mining far from
  the Core, and the thing it protects is *you*, not the base. Defense opens on the spike trap instead:
  the cheapest thing in the game that fights (no power, no ammo, no targeting).
- ⚠️ `conditioning` is the node that needs §0.3. It is listed last deliberately: if that fix is dropped,
  this row is what goes with it.

## 2. `Progression` — the spent state — `scripts/progression/progression.gd`

- `var taken: Dictionary[String, int]` (node id → level taken), `func node_level(id) -> int`,
  `signal node_unlocked(id: String, level: int)`.
- `func can_take(id) -> bool`: the node exists, `node_level < max_level`, every prerequisite is at
  level ≥ 1, and `upgrade_points >= point_cost`. ❗️**It deliberately does not consider
  `resource_cost`** — see §7: this autoload is node-free by design (`progression.gd:3-5`), it has no
  player position, and `Items.gather_available` needs one. Asking it would be the first line of this file
  that reaches into the scene.
- `func take_node(id) -> bool`: spends the points, bumps the level, emits `node_unlocked`. The **caller**
  has already paid any resource cost.
- `_multiplier(stat_name)` stops returning a flat 1.0: `1.0 + Σ(stat_per_level × level)` over every taken
  node naming that stat. Additive within a stat (two `mining_speed` nodes read as one sum) and neutral
  for a stat no node names, which is what keeps `ItemStats.effective_*` asking for buffs that do not
  exist. ⚠️ `mining_speed` is absent from `_PER_LEVEL` on purpose (`progression.gd:26-30` — "it's the
  skill tree's job"); the node lands on the multiplier, not on that table.
- `reset_run()` clears `taken`. One new line in a function whose whole job is to be complete;
  [save.md](../systems/save.md) already names "spent nodes" as 4.3's, so no doc change is owed there.
- ⚠️ **No yield state lives here.** The fractional-yield credit is per MACHINE (§3), so this autoload
  holds none of it.

## 3. The yield accumulator — on `Deployable`, not on the autoload

❗️**A ×1.1 multiplier on an output of 1 is 1 forever if it is floored, and non-deterministic if it is
rolled** — and a random tick contradicts [automation.md](../systems/automation.md)'s determinism. So it
accumulates, and `scripts/automation/deployable.gd` already carries `_power_accum` + `spend_power_tick`:
the exact "fractional thing resolved into whole ticks, per machine" idiom this needs, and the reason the
shape is already blessed. Add beside it:

- `var progression: Node = null` + `func _progression()` — the injectable-test-seam idiom.
  ⚠️ **`Turret` already declares its own** (`turret.gd:40, 257-260`) and GDScript refuses to shadow a
  base member: the turret's copy is **deleted** in this commit and its call site reads the base's. Net
  win — one injection point for three machines instead of three.
- `var _yield_credit := 0.0` — per instance by construction, so two miners never share a counter.
- `func apply_yield(base: int, stat_name: String, cap: int) -> int`:
  `total = base * get_stat(stat_name) + _yield_credit`; `whole = mini(floori(total), cap)`;
  `_yield_credit = total - whole`; return `whole`.
  - It banks **only what it hands out**, so a bonus a full slot cannot take is kept for the next call
    rather than destroyed — the same conservation `spend_power_tick` keeps for ticks.
  - ⚠️ **Neutral by construction at ×1.0**: `base * 1.0` is exact for the small integers involved, so the
    credit never moves until a node is taken. That is the property to test, not the arithmetic.
- ⚠️ **Per machine, not per player**, which reverses this file's earlier draft. The buffs now apply to
  deployables only (§4), so one pool on the autoload would be a counter shared between machines that
  never see each other. The cost is that the credit is per-entity state — deliberately **not**
  serialized at 4.3, because at most one item per machine is lost across a reload, which is not worth a
  save field. [save.md](../systems/save.md) gets one line saying so.

## 4. The three missing buff seams — one site each

None of these exists today (§0.2), and **both yields are FACTORY buffs: deployables only.** Player mining
and hand crafting are untouched, which is what keeps the drop path out of it entirely.

**`resource_yield` — `scripts/automation/miner.gd::on_tick`.** Compute
`apply_yield(extract_count, "resource_yield", room)` **before** `extract_reserve`, matching the existing
"room is checked BEFORE extracting" rule (`miner.gd:128-131`) — the seam has no way to hand ore back into
the ground.
- ❗️**`extract_reserve` still takes only `extract_count` from the deposit; the bonus is CREATED.** The
  cursor inspector puts "Copper Deposit — 43 ore left" on screen ([ui.md](../systems/ui.md)), and a bonus
  billed to `reserve` would make that readout a lie and a deposit unplannable. The buff means *more ore
  per unit of reserve*, which is what a yield buff should mean.

**`crafting_yield` — `scripts/automation/crafting_station.gd`.** Resolve the yielded count **before** the
`_room_for(recipe.output.id)` stall check (`crafting_station.gd:127`) and pass it to `_store_output`, so
back-pressure sees the real number and the credit is never spent on a craft that stalls.

**`crafting_speed` — the same `on_tick`.** Compare progress against
`maxi(1, ceili(recipe.ticks / get_stat("crafting_speed")))` with `>=`, not `==`.
- ⚠️ The `maxi` is not cosmetic — a large enough multiplier divides to 0 and a station at 0 ticks crafts
  every tick forever, the exact failure `test_recipe_defs` already asserts against for hand rows. And
  taking the node *mid-craft* drops the target below the accumulated progress, which `==` would step
  straight past.

**Untouched, deliberately:** `scripts/items/pickup_spawner.gd` (the player's own dig),
`CharacterScreen.craft` (hand crafting), and `Deployable.pop_to_pickup`. That last one is why the spawner
stays out of it: `spawn_at` is also the drop path for a swung-down machine, so a multiplier there returns
**two turrets for one**.

## 5. The player absorbs a max-stat node — `scripts/player/player.gd`

§0.3's fix. Extract the body of `_on_leveled_up` into `_absorb_max_gain()` and connect
`Progression.node_unlocked` to it as well. Both paths then raise the ceiling and the current value by the
same delta and refresh the cache — no double-dip, and a `conditioning` point is felt immediately rather
than at the next level.

## 6. Recipe gating — `data/recipe_defs.gd`

The `unlocked_by` column exists and is empty on every row; this fills it
([progression.md](../systems/progression.md) §Recipe tiers owns the column, and it is the "no consumer
change" claim being cashed).

- **Free forever (`unlocked_by = ""`): `pickaxe_t1`, `ladder`, `torch`.** Everything else names a node
  per §1's roster.
- ❗️**A `pickaxe_t1` hand row is NEW.** There is no pickaxe recipe today — `STARTING_KIT` hands one over
  and that is the only source. With the rest of the table gated, "what can I make at level 1" needs an
  honest answer that is more than light and a way back up.
  - ⚠️ **It breaks an existing assertion.** [3.6b](3.6b-crafting-tab.md)'s verification pinned "every
    hand-recipe output resolves to something with a `place_scene`". A pickaxe has none. The assertion
    splits: a hand output must resolve through `ItemDefs.stats_for` to an **authored** row (present in
    `ItemDefs.STATS`), and *placeables* additionally carry a `place_scene`.
- ❗️**Obtainability is now a property of the tree, and gets the test the bootstrap subset already has.**
  Two pins: every root node costs points only (§1), and every recipe's `unlocked_by` names a node that
  exists in `SkillDefs` (the cross-check that makes §0.1's single-source-of-truth real in both
  directions — no orphan gate, no node gating nothing).
- ⚠️ **A fresh run must reach level 2 by hand.** `xp_to_level(1)` is 50 and mining pays
  `MINING_XP_PER_BLOCK = 1.0` plus per-material loot XP, so it is a few dozen blocks — inside the first
  4:00 countdown, but it is a number 4.6 should look at now that a level is the gate on the factory
  rather than a stat bump.
- The F3 factory rig and the give-item dropdown still hand out machines directly. That is what a debug
  affordance is for, and it is now also the **only** way to see the late chain without playing to it —
  worth remembering when the browser check of the tick is next needed ([ui.md](../systems/ui.md)
  §Build factory rig).
- ❗️Land this **after** §1–§5, never before: it is the commit that makes the game harder to obtain, and
  the tree that opens it back up has to exist first.

## 7. The tree tab — `scripts/ui/character_screen.gd` + `scenes/ui/character_screen.tscn`

The tab is [ui.md](../systems/ui.md) §Character screen's; it is a third tab in this window, not a screen.
`SkillsPage` today is a `CenterContainer` holding the label "The skill tree lands at 3.7."

- **Scene:** `SkillsPage` becomes a `VBoxContainer` — a points Label, then a `ScrollContainer` around a
  plain `Control` named `TreeCanvas` with a `custom_minimum_size` big enough for the authored positions.
  - ❗️**A plain `Control`, never a container.** A `VBox`/`Center`/`GridContainer` re-lays-out its children
    every frame and would overwrite the `position` each node carries — the hand-placed coordinates
    would simply not survive being set.
  - ⚠️ Set no `offset_*` without the matching anchors; a negative offset under `anchors_preset = 15`
    renders off-screen while `visible` stays true, which is a bug that looks like a missing feature.
- **Edges before nodes**, drawn with `draw_line` from a handler connected to `TreeCanvas`'s **`draw`
  signal** — no new script. ⚠️ Considered and rejected: a `class_name SkillTreeCanvas` node script. It is
  cleaner on paper, but the screen owns the transaction (it is where `items`, `progression` and `_player`
  are injected), so a separate node would be plumbing plus a class-cache regen for one `_draw`. The
  crafting tab is already ~200 lines of this file; the tab is built the same way.
- **Buttons built once in `_ready`** with the rest of the window, never on open and never on tab switch —
  [3.6a](3.6a-window-and-inventory.md) §6's browser-hitch rule, which the crafting rows already obey.
- Node text is `display_name` + `Lv n/max`; tooltip is `description`, the point cost, any `resource_cost`,
  and what it unlocks (via §0.1's `RecipeDefs.unlocked_by`). Taken / available / locked are theme colour
  overrides, added and **removed** rather than set through `modulate` — the `MISSING_INPUT_COLOR`
  precedent (`character_screen.gd:61-65`).
- ❗️**Reuse the 3.6b repaint `Timer`, widening its condition to "crafting OR skills tab".** A node with a
  `resource_cost` is affordable or not depending on **where you are standing** — the identical problem the
  timer was introduced for. Without this, walking to a chest leaves `emplacements` greyed, which reads as
  broken ([ui.md](../systems/ui.md) §Character screen). `_update_craft_timer` and its two call sites
  (`_show_tab` *and* `_set_open` — neither sees both halves alone) are already correct; only the
  predicate changes.
- **The spend transaction, in this order** — points and prereqs, then resources, then record:
  1. `progression.can_take(id)` — cheap, and it is the check that cannot be paid for.
  2. If `resource_cost` is non-empty (§0.4), `items.consume_available(_player.global_position, cost)`;
     bail on false.
  3. `progression.take_node(id)`.
  ❗️**Any other order eats the ore.** Consuming first and then discovering there is no point left is an
  item sink with no error message — the same failure `consume_available` is itself two-phase to avoid,
  and the "offer first, consume second" rule the quick-move and hand-feed paths already keep.
- ❗️**A `node_unlocked` unlock must re-filter the crafting rows.** With locked rows *hidden*,
  `_apply_recipe_filter` runs only at build time and on a category press — so a recipe unlocked while the
  window is open would stay invisible until the next category click. Connect `progression.node_unlocked`
  to a repaint that calls it.
- **Locked crafting rows stay hidden**, as shipped: `row_is_listed` keeps its meaning, and the tree tab is
  where a locked recipe is named.
  - ⚠️ `row_is_listed` is `static` and pure, and `test_character_screen.gd:1120-1130` pins it with
    synthetic rows. It must **take the unlock lookup as a parameter** rather than reaching for the
    autoload — otherwise it stops being testable without a `Progression` and quietly ignores the injected
    one, which is the seam the whole suite is built on.
  - ⚠️ With almost everything locked at level 1, `categories_for_station` still yields five buttons and
    four of them filter to nothing. Cheap fix in `_apply_recipe_filter`: hide a category button with no
    listed rows.
- **Unspent points get surfaced here, which [ui.md](../systems/ui.md) §HUD defers to exactly this step**
  ("deliberately not surfaced until there's a skill tree to spend it in"). The points Label on the page,
  plus a suffix on the tab button (`Skills (K) •2`) so it is visible from the other two tabs. The screen
  must connect `progression.leveled_up` to refresh both — it does not listen to it today.
