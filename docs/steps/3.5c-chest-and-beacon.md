## Scope & exit criterion

The two Utility deployables ([automation.md](../systems/automation.md) §Categories → Utility).

**Exit criterion:** an inserter fills a chest and pulls back out of it; dying near a beacon respawns you
there rather than at the Core.

---

## 1. `Inventory` gains a slot count — `scripts/items/inventory.gd`

The chest is the **first N-slot container in the game**. Every machine so far holds one or two bare
`Dictionary` fields (`CraftingStation._input`/`_output`, `Generator._fuel`, the miner's output slot, a
conveyor's slot); a chest must not become a third shape.

`Inventory` is already a player-agnostic `RefCounted` with change signals — nothing in it references the
player — so the chest can simply own one.

- `func _init(slot_count := SLOT_COUNT)`, plus `func slot_count() -> int`.
- The `SLOT_COUNT` loops in `add_item` (`:36,46`), `count_of` (`:103`) and the clamp in `take_range`
  (`:76`) become `_slots.size()`.
- Every existing caller constructs `Inventory.new()` and is unaffected; the ~15 test references to
  `Inventory.SLOT_COUNT` keep meaning the player's 40. `HOTBAR_SIZE` and `STACK_SIZE` are untouched.

## 2. `Chest` — `scripts/automation/chest.gd` + `scenes/automation/chest.tscn`

`class_name Chest extends Deployable`, holding one `Inventory.new(CHEST_SLOTS)` (20). 1×1,
`support_dirs = 15`, `power_demand = 0`, `removal_hits = 2`, `item_id = "chest"`. One `ColorRect` child
named `Visual` (the ghost preview is probed off its **offsets**, `deployable.gd:532-546`).

**No tick and no registry** — an inserter reaches it through `Terrain.get_entity` plus the transfer seam,
so a chest joins nothing in `Automation` and needs neither `on_placed` nor `on_removed`.

The transfer seam ([automation.md](../systems/automation.md) §The transfer seam; the header at
`deployable.gd:312` names the chest by name as a consumer):

- `accept_item(id, count)` → `count - _storage.add_item(id, count)`. `add_item` already fills partial
  stacks before empty ones and **returns the leftover**, which *is* the seam's contract ("how many it
  took; a partial accept is legal and the caller keeps the remainder"). No new logic.
- `extract_item(max_count)` → the first non-empty slot via `remove_from_slot`, returned as a detached
  `{id, count}`.
- `take_cargo()` → `take_range(0, slot_count())`. Destructive by contract, and it already returns
  detached duplicates.
- `func storage() -> Inventory` — the **3.6 seam**. [ui.md](../systems/ui.md) §Character screen's
  container view and `Items.gather_available(player_pos)`
  ([progression.md](../systems/progression.md) §Crafting range) both read this, and they bind
  `slot_changed` exactly as the HUD hotbar already does. One line now, no rewrite later.

**No container UI here, on purpose.** [player-combat.md](../systems/player-combat.md) §Hand-feeding
defers the interact-key container panel with drag-and-drop to 3.6 ("Building it here would write
drag-and-drop twice"), and there is no `interact` input action yet. That is **not** a dead end in the
meantime: inserters move items both ways, RMB hand-feeds one item per click, and swinging the chest down
pops every stack onto the floor through `take_cargo`. A chest is already fully usable by hand and by the
factory — 3.6 adds the *view*, not the function.

## 3. `RespawnBeacon` — `scripts/automation/respawn_beacon.gd`

[player-combat.md](../systems/player-combat.md) §Death & respawn already locks the intent: "A crafted
**beacon** overrides the respawn point (Day 3)." `_tick_respawn` (`player.gd:239-254`) hardcodes the
`&"core"` group today, and `core.base_cell()` is the anchor it reads.

- `class_name RespawnBeacon extends Deployable`, 1×1, `support_dirs = 15`, `power_demand = 0`,
  `removal_hits = 2`, `item_id = "beacon"`, in group `&"respawn_beacon"`. Unpowered:
  [automation.md](../systems/automation.md) §Categories files the beacon under Utility with the torch and
  the chest.
- `_die()` (`player.gd:213-223`) records `_death_position`.
- `_tick_respawn` asks a new `_respawn_anchor() -> Node2D`: the **nearest beacon to the death position**,
  falling back to the `&"core"` group. The existing `if core != null` guard already means "no anchor →
  stay where you are", so the fallback shape is unchanged.
- ❗️**Nearest-to-death, and a group query — not a `static var instance`, not most-recently-placed.**
  - A `static var instance` set in `on_placed` would **dangle across the scene reload**: deployables are
    children of `Main` and die with the reload *without ever being popped*, so `on_removed` never runs.
    That is the exact trap `automation.gd:268` documents for the tick registries, and it would need its
    own `reset_run` hook to remember. A group query dies with the scene for free.
  - Most-recently-placed is **not stable across [save.md](../systems/save.md)'s restore-in-file-order**,
    the same argument that made the tick iterate row-major rather than by insertion order. Nearest-to-death
    is derived from the world, so it is identical on reload.
  - It is also the better game rule: you build beacons across the map and come back at the one nearest
    where you fell.
- `respawned` grows a payload the HUD can read — `hud.gd:409` hardcodes `"Respawned at the Core"`, which
  would otherwise lie. Keep the string choice in the HUD, not in the player.

## 4. Wiring

`data/items/chest.tres` and `data/items/beacon.tres` (`ItemStats` with `display_name`, `icon_color`,
`place_scene`; `torch.tres` is the minimal template), plus `const` preloads and `STATS` rows in
`data/item_defs.gd`. That alone earns each a HUD icon and an F3 give-item row (`debug_menu.gd:198`) — the
F3 factory rig needs **no** change, since neither is part of the production chain the rig demonstrates.

## Verification

- **After each new `class_name` script** (`Chest`, `RespawnBeacon`): regenerate the class cache with a
  headless `--editor --quit` pass, or CLI runs fail on the unknown class with no useful error. Then
  format and check LSP diagnostics.
- **Unit tests** follow `tests/automation/`'s fixture shape (fresh `Terrain` in the tree, `GameScript`
  out of the tree at `BUILD_PHASE`, `Automation` with both injected and `set_process(false)`). Neither of
  these draws power, so **no `Supply` double is needed** — unlike [3.5a](3.5a-turrets-and-traps.md)'s
  turret and press.
  - `test_chest`: seam round-trip (accept partial when nearly full, extract, refuse nothing),
    `take_cargo` empties it, and an `Inserter` moves items in *and* out through the real tick.
  - `test_respawn_beacon`: nearest-of-two wins, removal falls back to the Core, and no beacon behaves
    exactly as 2.5 did. `tests/player/test_player.gd:399-466` is the existing death/respawn block and
    never asserts position, so these are additive.
  - `tests/items/test_inventory.gd` gains a case for a non-default slot count.
- **By hand:** place a chest, hand-feed it (RMB), point an inserter into it and another out of it, watch a
  belt fill and drain; swing the chest down and confirm every stack drops. Then place a beacon far from
  the Core, F3 → kill player, and confirm you respawn at the beacon and the banner says so — then remove
  the beacon and confirm you go back to the Core.
