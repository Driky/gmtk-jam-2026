# Step 3.5b — Ladder & climbing

**This file owns no decisions.** It is an execution checklist, like [roadmap.md](../roadmap.md): every
decision below names its owning doc, and the "Doc reconciliation" section lists the owning-doc edit this
step must make **in the same commit** as the code. Never restate a decision here as if this file owned

Siblings: [3.5a](3.5a-turrets-and-traps.md) · [3.5c](3.5c-chest-and-beacon.md). **Do this one last** —
it is the only sub-step that touches a predicate four other systems read *plus* the flow field *plus*
mob locomotion.

## Scope & exit criterion

The first climbable, for the player **and for mobs**.

**Exit criterion:** a ladder column built up from the floor, climbed by the player with `W`/`S`, climbed
by a walker during a wave, and popping bottom-up in one frame when its floor tile is mined.

**Mobs use ladders, and this is not optional.** [enemies.md](../systems/enemies.md) §Climbables already
**locks** biped-only mob climbable use ("player ladders are biped highways during waves — remove
pre-wave, hide behind hatches, or favor poles, which mobs can never ascend. Deliberate emergent
texture"). Shipping a player-only ladder would contradict the owning doc and hand the player a speed
advantage the wave does not get. `EnemyStats.is_biped` (`enemy_stats.gd:25`) is commented "Gates
climbable use (Day 3)" and nothing reads it yet — this step is what reads it.

**Cut line ✂️8 is not fired.** It reads "Rope/pole climbables (**ladder only**)", so shipping the
symmetric ladder now and leaving rope/pole plus the *directional* profiles to 4.1 is the pre-authorized
shape, not a compromise. A ladder is the symmetric case (up and down at full speed), which is why it
needs no profile mechanism at all.

⚠️ **This step does not close the isolation hole.** A mob can only climb a ladder the *player* built.
The open hole — vertical air gaps are not diggable, so a floating platform or an overhang soft-locks
ground mobs — is written up at the end of [3.5a](3.5a-turrets-and-traps.md) and its fix is roadmap 4.1.

## 1. One predicate, four readers

`@export var is_climbable := false` on `Deployable`, plus
`static func climbable_at(terrain: Node, cell: Vector2i) -> bool`, mirroring the existing
`is_deposit_at` / `has_deposit_in` idiom (`deployable.gd:157-168`).

**Four** things read it, which is exactly why it must be one predicate rather than four copies of the
same question: the player's climb (§3), the flow-field snapshot (§4), `EnemyLocomotion.decide` (§4), and
`Enemy._attackable_entity` (§4).

❗️**This single export also carries the support-stacking rule.** A separate `stack_group` export would
be a second name for the same set: the stacking rule *is* "a climbable is held up by the climbable below
it", and 4.1's rope and pole get it for free by authoring `is_climbable`. This resolves the clause
[automation.md](../systems/automation.md) §Deployable base explicitly parked here ("Support means a solid
TILE neighbour — a deployable never holds up another deployable. […] If ladders want to stack on each
other, that second clause lands at 3.5").

## 2. The support clause — asymmetric, and the naive version is a real bug

❗️**With a symmetric "a climbable neighbour holds me up" clause, two ladders floating in mid-air each
point at the other and both claim support forever.** `is_supported_at` is a **one-step predicate, not a
reachability query**, so it cannot see the cycle. Nothing would report it; you would just have ladders
hanging in the void.

**Fix: the clause is directional — a rung is held by the rung BELOW it, only.** The relation then
strictly increases in `y` toward a solid anchor, so a cycle is impossible *by construction*, and you
build a column bottom-up from the floor, which is the direction you climb anyway.

- `is_supported_at(terrain, origin, area, dirs, climbable := false)` — a **defaulted** fifth argument, so
  every existing call site is untouched *by construction*. That is the same bargain `facing`/`harvests`
  made at 3.3 ([automation.md](../systems/automation.md) §Deployable base), and it is why the 3.1
  behaviour is preserved by construction rather than by re-testing it.
- `Deployable.scene_is_climbable(scene)` joins the probe cache beside `scene_size` / `scene_harvests`
  / `scene_power_radius` (`deployable.gd:444-522`), under the same anti-drift contract: read off an
  authored instance, never a second copy of the answer.
- `Player.can_place_at(..., climbable := false)` (`player.gd:606-628`) and a
  `Player.placement_is_climbable(item_id)` static beside `placement_harvests` (`player.gd:668`).
- ❗️**`MiningCursor` must pass the new argument.** The ghost's validity *is* the same `can_place_at`
  the click runs ([player-combat.md](../systems/player-combat.md) §Placement: "its validity is literally
  the same `can_place_at` the click runs, so it can never promise something the click refuses"). Miss
  this and a ladder column tints red exactly where the click accepts — the one thing that invariant
  exists to prevent.

**The cascade needs no new machinery.** [automation.md](../systems/automation.md) §Support & popping
proves termination by *counting* ("every step either does nothing or permanently removes one deployable,
and only a removal can enqueue more"), which is independent of chain depth — only the number of steps
grows, and `MAX_DRAIN_STEPS = 4096` still backstops it. That section already says outright that "pops
during the drain append to the array being drained — **that append is the cascade**". Mining the floor
under a 20-rung column pops rung 0, whose `remove_entity` emits `entity_changed`, which probes rung 1,
and so on: one rung per drain step, iterative, never recursive. The ordering is right too —
`pop_to_pickup` frees its cells *before* emitting (`deployable.gd:257-266`), so the rung above sees a
genuinely empty cell.

Tests, one per plausible-wrong-answer:
- Two ladders in mid-air are **not** supported (the acyclicity test).
- A rung is held by the one **below** and **not** by the one above (the orientation test the
  `SUPPORT_OFFSETS` comment at `deployable.gd:13-15` demands).
- A floor-anchored column of N pops entirely in one `drain_support_queue()`.
- A non-climbable deployable behaves exactly as it did at 3.1 (the defaulted-arg guarantee).

## 3. `Ladder` + player climbing

`class_name Ladder extends Deployable` — 1×1, `support_dirs = SUPPORT_ALL`, `is_climbable = true`,
`removal_hits = 1`, `power_demand = 0`, no tick and no registry. The `class_name` exists only so the
climb can cast.

`_move()` (`player.gd:389-407`) is 18 lines with **no state machine** — the only mode-ish flags are
`_stun_left` and `is_dead()`. `move_up` / `move_down` are declared in `project.godot:54,60` and are
**completely unused**, so `W`/`S` are free.

Deployables carry **no collision bodies at all** (a torch scene is a `Node2D` + a `ColorRect`), and the
player's mask only sees the tilemap, so climbing cannot be physics — it is a grid query, exactly as
`loot_bag.gd:39-46` already asks `Terrain.is_solid` directly instead of carrying a body.

```
# In _move, after velocity.x is set, BEFORE the gravity block:
if _try_climb():
    move_and_slide()
    return
```

- Probe `Deployable.climbable_at(Terrain, Vector2i((global_position / TILE).floor()))` — the cell under
  the player's centre. False → drop the latch and return false.
- ❗️**Latched, not automatic.** Engage only when `move_up`/`move_down` is held; otherwise walking past
  a ladder on flat ground, or brushing one mid-jump, sticks you to it. Once engaged, stay engaged until
  you leave the ladder cell or jump.
- `velocity.y = Input.get_axis("move_up", "move_down") * CLIMB_SPEED`; no gravity this tick.
- Set `_coyote = COYOTE_TIME` on each climbing frame and return `false` on `jump` just-pressed. The
  existing coyote + jump-buffer path then fires the jump itself, so stepping off the top of a ladder
  needs **no second jump implementation**.

Note the player is unaffected by the fall-damage concern in §4c — fall damage is mobs-only
([enemies.md](../systems/enemies.md) §Pathfinding).

## 4. Mobs climb — three non-obvious blockers, then the ordinary work

### ❗️(a) `_attackable_entity` eats the ladder before locomotion ever sees it

`_push_core` checks `_attackable_entity` at `enemy.gd:120` — **before** `EnemyLocomotion.decide` at
`:125` — and that helper keeps **every** deployable in the cell *ahead* (`:314-316`). So a mob facing up
into a ladder returns it as an attackable entity, stops, and chews it: the climb branch is unreachable
and the feature silently does nothing.

**Fix:** skip a climbable in the cell ahead **when `stats.is_biped`**. That is precisely what `is_biped`
exists for, it keeps a non-biped chewing the ladder as [enemies.md](../systems/enemies.md) §Climbables
intends, and it mirrors the existing narrow own-cell skip (§Locomotion resolution: "A `Deployable` in the
mob's own cell is skipped, **and only there**") rather than inventing a rule.

### ❗️(b) The stuck watchdog must count CLIMB as movement

[enemies.md](../systems/enemies.md) §Locomotion resolution warns that the own-cell skip exists partly
because "stopping for it takes an early return that skips the stuck watchdog, starving the very thing a
mob needs to escape a cycling route". `_update_stuck` (`enemy.gd:139-143`) lists WALK / FALL / JUMP as
moving. **CLIMB must join them**, or a mob wedged on a ladder never arms the direct-dig fallback and
hangs there for the rest of the wave.

### ❗️(c) Climbing down must not read as a fall

`_step` accumulates `_air_top_y` whenever the mob is off the floor (`enemy.gd:94`) and `_check_landing`
bills the drop as damage (`:173-179`). Descend ten rungs, step off, take ten tiles of fall damage. **The
CLIMB actuation resets `_air_top_y = INF`.**

### The ordinary work

- **`EnemyLocomotion`** (`enemy_locomotion.gd`) — `Action.CLIMB` joins the enum. In `decide`:
  - the `dir == Vector2i.UP` branch (`:48-54`) returns CLIMB into `above` when `stats.is_biped` and
    `climbable_at(above)`, **before** its current fall-through to NONE;
  - the `dir == Vector2i.DOWN` unsafe-drop branch (`:45-47`) does the same downward.
  `decide` is already pure and static with terrain injected, so both are unit-testable with no physics
  frame — the same decision/actuation split `FlowField` uses.
- **`Enemy._actuate`** (`enemy.gd:246-275`) — a CLIMB case setting `velocity.x = 0.0`,
  `velocity.y = signi(target.y - pos.y) * <climb speed>`, and `_air_top_y = INF`. Gravity is applied at
  the **top** of `_step` (`:91-95`), so writing `velocity.y` here overrides it for the frame.
  - ⚠️ Vertical speed is **`stats.speed`, not `stats.climb_speed`.** `climb_speed` is documented as
    wall-climbing (`enemy_stats.gd:24`, "0 = can't wall-climb") and belongs to 4.1's crawler; a walker
    has `climb_speed = 0` and **must** still use a ladder, because the gate is `is_biped`. Add a
    `LADDER_SPEED_FACTOR` const if full walk speed reads wrong.
- **`FlowField`** (`flow_field.gd`) — a `_climbable: PackedByteArray` filled inside the **existing**
  `_snapshot` entity walk (`:285-294`), which already iterates `get_entity_cells()` and reads properties
  off each entity, so this is one line in a loop that already runs. Resize + `fill(0)` beside
  `_sid.resize` (`:264`) — the entity walk is *sparse*, so a stale array would keep last solve's
  ladders.
  - The up/sideways edge (`:168`) gains `or (uy < vy and _climbable[u])`: an **ascending** move into a
    climbable cell is a `MOVE_COST` edge regardless of `_supported`. Mind the swapped roles documented
    at the top of the file — the edge being relaxed is the mob's move `v -> u`, and `uy > vy` is
    already the falling branch, so ascending is `uy < vy`.
  - Requiring only the **destination** to be climbable is deliberate: it lets a mob enter the column
    from the cell below the bottom rung, and the chain continues because each rung above is climbable
    too. That is [enemies.md](../systems/enemies.md) §Climbables' "cheap vertical edges" for the
    symmetric case; the *direction-respecting* half is rope/pole at 4.1.
  - Recompute triggering is **already wired** — `waves.gd:267` debounces on `entity_changed`, so
    placing or removing a ladder re-solves with no new plumbing.
- ⚠️ A ladder still carries its `_entity_cost` HP surcharge (`flow_field.gd:294`), so a ladder route
  costs ~0.2 more per rung at 20 HP — a fifth of one step, the same arithmetic
  [terrain.md](../systems/terrain.md) §Lighting does for torches. It mildly discourages ladder routes
  and blocks nothing. **Leave it**, and do not add a `blocks_mobs := false` escape hatch pre-emptively
  — that doc says so by name.

  1. Build a column up from the floor; the ghost must stay **green** the whole way (that is the
     `MiningCursor` wiring).
  2. Climb it with `W`/`S`; jump off the top and land normally.
  3. Mine the floor tile under rung 0 — the whole column pops bottom-up in one frame.
  4. Leave a ladder up over a wave: a walker must **climb** it, not stand at the bottom chewing
     (blocker a), not hang on it forever (blocker b), and not die on stepping off the bottom
     (blocker c).
