# Progression & Items

Owner of: XP, levels, the skill tree, recipe tiers, crafting range, item content.

## XP & levels
All sources route through `Progression.grant_xp(source, amount)`. The caller decides the amount, so each source stays independently tunable; `source` is only tallied (`xp_by_source`), never branched on — that tally is what the Day-4 balance pass reads to answer "where is XP actually coming from".

| Source | Amount |
| --- | --- |
| Mining | **Flat per block broken** (`MINING_XP_PER_BLOCK`), *not* per hardness — depth is rewarded through what a block drops, not through how long it took to break, so a slow tool can't out-earn a fast one |
| Looting | Per-material `loot_xp` (data/materials.gd) when a dropped item is **collected**: ore beats non-ore, rarer ore beats common ore. This is the channel that makes digging deeper pay |
| Kills | `EnemyStats.xp` |
| First-time crafts | ~~Reserved~~ — **cut at 3.6b** |

❗️**The 3.7 yield buffs pay no XP either, and that falls straight out of the rule below rather than needing a clause.** Both live on machines — `resource_yield` on the miner, `crafting_yield` on the crafting station (§Skill tree) — and machine-extracted ore already misses both channels by construction. A yield buff on the *player's* dig would have been an XP multiplier as well as an item one, which is the second reason the pickup spawner is not one of its sites.

**Automation is worth zero on both channels (3.3).** ❗️Machine-extracted ore pays nothing: `Terrain.extract_reserve` deliberately emits no `drops_spawned` (the ore goes into the machine, never onto the floor), so it misses the looting channel by construction, and the mining channel is already gated on `source == Source.PLAYER`. Both halves are code that existed before the miner did — the anti-farm rule falls out rather than being enforced. Without it a miner is an XP fountain you walk away from, which is the one thing a factory must never be. **Smelting pays nothing either**: bars are absent from `loot_xp`, so a furnace line is not a second channel.

❗️**First-time-craft XP is CUT (3.6b), not deferred**, and this table says so rather than leaving a "reserved" row that quietly never lands. It needs a `crafted_ids` set on this autoload plus its own `reset_run` line, and it pays exactly once per recipe — so it is a one-off trickle that stops mattering the moment you have crafted everything, bought at the price of a second piece of run state to serialize at 4.3. **Crafting is therefore not an XP channel at all**, which leaves mining, looting and kills as the three, and keeps the anti-farm argument above whole: nothing you build pays XP, in any direction.

**Player-placed blocks are worth zero on both channels** — no mining XP when re-broken, and their drop grants no loot XP. Without it, walling and re-mining the same block is the cheapest XP in the game. Enforced by a `player_placed` flag on the tile ([terrain.md](terrain.md)) carried into the drop. Recovering your own loot bag likewise grants nothing: bags hand items straight to the inventory and never spawn pickups, so they miss the loot channel by construction ([player-combat.md](player-combat.md)).

Curve: `xp_to_level(L) = 50 * L^1.6` (tune — expect it to be too generous first playtest). Level-up grants flat stats (+HP, +mana, +move speed) and **1 upgrade point**; the player's *current* HP/mana rise by the same delta as the maximum, so a level-up is a reward rather than a mid-wave heal button.

## Skill tree (locked: one mixed tree)
Nodes are `SkillNode` Resource files (`scripts/progression/skill_node.gd`, registered in `data/skill_defs.gd`): `id`, `display_name`, `description`, `prerequisites[]`, `point_cost`, optional `resource_cost{item: count}`, `max_level`, a `stat_name`/`stat_per_level` pair, and a hand-placed `position`. Buffs apply as multipliers read via one lookup, `Progression.get_stat(name)` — no scattered special cases. That lookup is one formula serving both kinds of stat it has to carry (absolute values like `max_hp`, multipliers like `mining_speed`): `(base + per_level_flat * (level - 1)) * multiplier`. Base defaults to 1.0 and per-level to 0.0, so an unknown stat reads a neutral 1.0 — which is what lets `ItemStats.effective_*` ask for buffs that don't exist yet. ✅ **Landed at 3.7** ([step doc](../steps/3.7-skill-tree.md)) as 13 nodes across three branches; the run's spent state is `Progression.taken` (`node_level` / `can_take` / `take_node` / `node_unlocked`). Tree UI ([ui.md](ui.md)): node graph with hand-placed positions stored in the Resource.

- ❗️**`unlock_recipes[]` is STRUCK (3.7).** A node unlocking a recipe and a recipe naming its gate are one edge, and this doc used to store it on both sides — one fact with two writable copies, free to drift the first time a recipe moves branch. The recipe row's **`unlocked_by` wins**: it shipped at 3.6b and the crafting tab already filters on it. A node's unlocks are the query `RecipeDefs.unlocked_by(node_id)`, in table order, beside `for_station` and `categories_for_station`.
- ❗️**`can_take` deliberately ignores `resource_cost`.** This autoload is node-free by design, and a resource check goes through `Items.gather_available(player_pos)` (§Crafting range) — a player position it must never reach for. The **screen** owns that half, in the order `can_take` → `consume_available` → `take_node`; any other order eats the ore on a node it then cannot grant. ⚠️ And `consume_available` is called **only for a non-empty cost**, because it refuses an empty one by design (ibid.) — calling it unconditionally would make every point-only node unbuyable.
- **The multiplier is additive WITHIN a stat, not compounding**: two nodes each granting +10% read as +20%, so a third is a number a designer adds up rather than a product to work out. Levels multiply the node's own rate.
- ❗️**Both yields are FACTORY buffs, on deployables only (3.7).** `resource_yield` is the miner's, `crafting_yield` is the crafting station's; the player's own dig and hand crafting are untouched. `PickupSpawner.spawn_at` is deliberately excluded because it is also `Deployable.pop_to_pickup`'s drop path — a multiplier there returns **two turrets for one**. That is why every yield node sits behind `mechanization`: bought before you own a machine, it would be a point spent on nothing.
- ❗️**A fractional multiplier on an integer output accumulates, per MACHINE.** The credit lives on `Deployable` beside `_power_accum` ([automation.md](automation.md) §Deployable base) — not on this autoload, which holds none of it. A flooring `+10%` on an output of 1 is 1 forever and a rolled one contradicts the tick's determinism.
- **A node that raises a MAXIMUM emits through `node_unlocked`, which the Player absorbs through its level-up code** ([player-combat.md](player-combat.md)). Raising the ceiling outside that path leaves the player's cached maximum stale, so the next level-up pays the level's delta *plus* the node's.
- ❗️**Every root costs one point and NO resources.** A level-2 player has exactly one point and whatever ore they dug by hand, so a root priced in bars is the same deadlock the bootstrap-recipe rule forbids one tier down (§Recipe tiers). Pinned by a test, like that rule is.
- ⚠️ **`power_grid` sits between `logistics_i` and `mechanization`**, which is the tree restating what that same rule keeps: the miner and the furnace both draw power, so unlocking them first hands the player two machines that cannot run and nothing to run them off.

**Tree size is the designated scope lever** — see cut lines in [plan.md](../plan.md).

## Recipe tiers
Recipes span tiers across automation / logistics / power / defense / components, unlocked by tree progress. Recipe specifics are decided during implementation as data, not pre-designed.

**The table landed at 3.3 as `data/recipe_defs.gd`** — static and pure, mirroring `data/item_defs.gd` exactly, which is where 2.5 put the *item* half of this DB. Per row: `station` (matched against a `CraftingStation`'s authored `station_id`), `inputs` as `{item_id: count}`, one `output` `{id, count}` stack, and `ticks` at 10 Hz. Two queries: `for_station(station)` (table order, which is also selection order, so "first match wins" is a property of the file rather than of whoever iterates it) and `accepts_input(station, id)` — the id-routing predicate a station's `accept_item` is built on ([automation.md](automation.md) §Categories).
- ❗️**`inputs` is a map from day one**, even though a one-input-slot furnace can only ever match a single-input row. Widening the *key* of a shipped table later is a rewrite of every consumer; carrying the extra key now costs nothing, and 4.2's assembler needs it.
- **3.6b is the crafting UI over this table, not a second one.** The roadmap's "item/recipe DB" bullet reconciles down to that UI.
- ✅ **`station = "hand"` joined `furnace` / `ammo_press` at 3.6b, and it is what makes the game obtainable.** Every deployable reached the player before it only through the F3 give-item dropdown or the factory rig, and an exported build has no console — the starting kit is a pickaxe and torches. Hand rows are the door. They cost no new mechanism: `for_station` and `accepts_input` already filter on that string, and **`ticks` is ignored on the hand path, so every hand row is `ticks = 0`** — split by station in the table's own assertion, since a station row at 0 would craft infinitely on one tick. ⚠️ Hand rows are invisible to a real station **only because no scene authors `station_id = "hand"`** — a furnace would eat their inputs the day one does, so that is pinned by a test that scans `scenes/` rather than left to luck.
  - **Thirteen rows, one per placeable deployable**, priced in `stone`/`copper`/`coal`/`iron` and the two bars. Counts are placeholders (balance is 4.2/4.6); their only job is to make *mine → smelt → craft* reachable. ❗️**The bootstrap subset is load-bearing and not a balance number**: `furnace`, `generator` and `miner` cost **only directly-mined materials, never bars**, because all three carry `power_demand = 1.0` — smelting needs a generator, so a generator priced in a bar is a deadlock whose only exit is the console. Both that and "every input is reachable by a `tool_tier = 1` pickaxe" are pinned by tests, which is also the pin on [terrain.md](terrain.md)'s tool-tier retune.
- ✅ **`unlocked_by` is filled in at 3.7, and it is what decides what a NEW RUN can build.** Three hand rows stay free forever — **`pickaxe_t1`, `ladder`, `torch`**: a tool, a way back up, and light. Everything else names a skill node, so obtainability moved off "there is a hand row for it" and onto the tree's roots (§Skill tree). Pinned exactly, not as a minimum: a row slipping out of the gate is a machine handed over for free, and a row slipping in is a run that cannot craft its way to level 2.
  - ❗️**The `pickaxe_t1` hand row is NEW at 3.7.** `STARTING_KIT` was the only source of a pickaxe, and with the rest of the table gated, "what can I make at level 1" needed a better answer than light. ⚠️ It is also the first hand output with **no `place_scene`**, which splits 3.6b's assertion in two: every hand output must be an **authored** `ItemDefs.STATS` row, and only *placeables* additionally carry a `place_scene` — a non-placeable one has to be a tool that actually mines.
  - ⚠️ **A STATION row carries no gate, deliberately**: it is gated by owning the station (you cannot smelt without a furnace, and `mechanization` unlocks one). A second gate on the row would be the same fact stored twice.
  - ⚠️ **A fresh run must now reach level 2 by hand**, which is a number 4.6 should look at: `xp_to_level(1)` is 50 against `MINING_XP_PER_BLOCK = 1.0` plus loot XP, so it is a few dozen blocks — inside the first countdown, but a level is now the gate on the whole factory rather than a stat bump.
- ❗️**Every row grows `category` and `unlocked_by` at 3.6b, filled or not.** `unlocked_by = ""` means always available, so 3.7's tree fills the column in with **no consumer change** — the same argument this file already makes for `inputs` being a map from day one: widening a shipped table's shape later is a rewrite of every reader. `category` is what [ui.md](ui.md)'s category filter groups on, and the values are **[automation.md](automation.md) §Categories' own** (`automation` / `logistics` / `power` / `defense` / `utility`, plus `components` for what a station makes) so the game has one taxonomy rather than a crafting one beside a deployable one. The distinct set, in table order, is `RecipeDefs.categories_for_station` — beside `for_station` because the order is a property of the file, not of the UI. There is deliberately **no name field**: a recipe is named by `Hud.item_name` of its output, which is already the one place that question is answered.
- **The ore-tier ladder starts at 3.5a with ammo**: one ammo tier per ore tier, each a `ProjectileStats` `.tres` plus an `ItemStats` `.tres` carrying it in the existing `projectile` field. The turret reads its shot **off the loaded ammo**, so a tier is that pair and two rows — never a table of its own, and never a stat on the turret. ⚠️ Copper and iron ship; `gold` and `magmatite` have no bar recipe until 4.2 and get theirs alongside it.
- Crafted outputs stay out of `Materials.LOOT_XP` — smelting and pressing are deliberately not XP channels (§XP), so ammo pays nothing on pickup.
- **`turret_damage`** (§Skill tree) now has a seam to land on: `ProjectilePool.fire`'s per-shot `damage_scale` ([player-combat.md](player-combat.md) §Combat), which scales a shared `ProjectileStats` without duplicating it per turret.
- Crafted outputs are authored `ItemStats` `.tres` with an `icon_color` and no `place_scene`, so they resolve a HUD icon and a give-item row for free and are not placeable. They are **absent from `LOOT_XP`** — see §XP.

## Crafting range
All crafting-cost checks — hand crafting, player-initiated station crafting, and tree `resource_cost` unlocks — draw from player inventory **plus containers within a radius of the player**, via one reused query: `Items.gather_available(player_pos)`.

"Containers" is the **chest** (3.5c), read through `Chest.storage()` — a live `Inventory`, so the query walks the same model as the player's own and the 3.6a UI binds the same `slot_changed` ([automation.md](automation.md) §Categories → Utility, which owns how a container is *found*). ✅ **Landed at 3.6b** as three functions on `scripts/items/items.gd`: `containers_near(player_pos)`, `gather_available(player_pos)` and `consume_available(player_pos, inputs)`. Radius is `CRAFTING_RANGE_PX = 12 * TileLayout.TILE_SIZE` — the reach radius is 4.5 tiles and would make you stand on the chest.

- **`containers_near` owns discovery AND order**, and both queries go through it. ⚠️ Its group loop is **untyped**, for the reason every stored collection in this codebase is, and it duck-types on `Node2D` + `storage()` rather than on `Deployable`: the radius filter already needs the position, and `storage()` is what makes something a container everywhere else. ❗️`Items` is an autoload `Node` so `get_tree()` resolves, and with no tree or no container in the group all three answer from the player inventory alone — headless tests are unaffected.
- ❗️**`gather_available` needs a `consume_available` counterpart, and that is the half most likely to ship broken.** The tally is a flattened `{id: total}` copy — it can *report* but not *remove*. A naive per-id removal loop that runs short halfway has already eaten the first inputs and produces nothing, which is an item sink with no error message. So consuming is **two-phase**: verify the whole cost, then remove. It lives beside `gather_available` because the two must share the same discovery *and* the same order — player inventory drained first, then containers in a **stated** order, so the outcome cannot drift across [save.md](save.md)'s restore-in-file-order. Same argument that made the tick iterate row-major.
  - **The stated order is row-major by `global_position` (y, then x).** `get_nodes_in_group` hands back scene-tree order, which is exactly what a save round-trip reshuffles. `consume_available` discovers **once** and reuses the list across both phases, so the pool it verified and the pool it drains cannot be different sets.
  - Draining goes through **`Inventory.remove_item(id, count) -> int`** ([player-combat.md](player-combat.md) owns that model), the mirror of `add_item`: it reports what it *actually* took, which is what lets the caller count what it still owes. Without it this file would walk slot indices from outside a model that already owns that loop.
  - ⚠️ An **empty** cost is refused rather than trivially granted: no row in the table has one, and treating it as payable would make a malformed row an infinite tap.
- ❗️**Equipment is excluded from both.** Crafting out of your worn helmet means the consume step can silently un-equip you, and "why did my armor vanish" is a bug report rather than a feature.
- ⚠️ **A crafted output must not vanish into a full inventory**: whatever does not fit lands on the floor, the same contract pickups and loot bags keep ([player-combat.md](player-combat.md)) — nothing is silently deleted.
