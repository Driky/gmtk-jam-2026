# Automation & Deployables

Owner of: the `Deployable` base, placement, all deployable categories, the 10 Hz tick, conveyors/inserters/machines, power grids.

## Deployable base & placement
All placeables share a `Deployable` base (`scripts/automation/deployable.gd`): grid footprint (**arbitrary W×H per type**, authored as an export), HP, faction, `on_placed/on_removed`, registered into `Terrain`'s entity dict per occupied cell. **The origin cell is the TOP-LEFT one**, so a footprint grows right and down from `cell()`. Registration is **all-or-nothing with rollback** (the `Core.register_footprint` rule, verbatim): a partial claim would leave cells nothing can ever occupy again. The Core keeps its own copy of that loop rather than becoming a `Deployable` — *not* being one is exactly what keeps it un-removable, with no special case anywhere. Placement feedback is a **modeless, always-on ghost**: no toggle, no binding, no "placement mode" to enter — a grid-snapped W×H ghost draws whenever the selected hotbar item is placeable, and nothing draws when it is not. `Player.placement_size(item_id)` is the whole question; `ZERO` means "not placeable". The power coverage overlay (3.4) joins the same ghost for powered machines.

The ghost is three layers: a **translucent preview of the item itself**, the per-cell **validity tint** over it (space empty, supported, in reach, not in a buffer zone), then the outline.
- ❗️**The preview is load-bearing, not decoration.** A footprint box alone is identical to the mining cursor at 1×1 — only the colour differs — so the ghost read as "the cursor turned green" rather than "here is your torch", and the W×H part that justifies the feature stays invisible until 3.3 ships a multi-cell machine. The preview is read off the scene's own `ColorRect` (the repo-wide placeholder-art convention), so it cannot drift from what actually gets placed; a block previews as its material's `base_color`. A deployable with no `ColorRect` degrades to tint-only.
- ❗️**Validity is drawn ON TOP of the preview.** A block fills its whole cell with its own colour and buried the green/red underneath — "can I put it here" has to survive whatever the item happens to look like.

**Facing (3.2).** Conveyors and inserters need a *direction*, which `support_dirs` is not — that is a support bitmask, and inverting the two would be a silent bug. So the base carries two separate things: an authored `@export var directional` ("does this care which way it points?") and a runtime `var facing` defaulting to `RIGHT`. Facing is deliberately **not** an export: the player holds a pending rotation, cycled with **R** (`rotate_placement`, Right → Down → Left → Up, clockwise on screen), and `_place_scene` stamps it on the instance before anything else reads the node. ❗️The pending rotation lives on the **player**, not per item — it is a property of the hand, so switching hotbar slots keeps it and a whole downward belt line is one R press rather than one per belt. The ghost draws a facing arrow when `Deployable.scene_directional(scene)` says so, in the **same** validity colour as the outline (a second colour there would read as a second signal), and reads the player's pending facing directly, so the arrow can no more disagree with the placement than the validity tint can. `scene_directional` joins `scene_size`/`scene_support_dirs`/`scene_visual` under the same anti-drift contract: the answer is read off an authored instance, never kept as a second copy. [save.md](save.md) already lists rotation as entity state, so nothing about the save format changes.

**Support is a direction bitmask** (`@export_flags("Up","Right","Down","Left")` → 1/2/4/8), not a fixed rule: a torch is all four (mounts on a wall, a floor *or* a ceiling), a ceiling lamp is `1` (Up), a standard turret and a spike trap are `4` (Down — a horizontal base under them), and `0` opts out entirely — that deployable never pops. **Support is authored per scene, so variants of one category may differ**: a ceiling turret would be `1` where the standard one is `4`, with no code change either way. This generalizes 2.7's cardinal-adjacency placement rule rather than replacing it, and one **static** predicate (`Deployable.is_supported_at`, terrain injected) serves both placement validity and the post-mine re-check, so the two cannot drift.
- **Support means a solid TILE neighbour — a deployable never holds up another deployable.** Chain depth is therefore 1 and cascades are a rare special case rather than the norm. If ladders want to stack on each other, that second clause lands at 3.5.
- **One supported cell holds the whole footprint up.** A 2×2 resting a single corner on a ledge is standing, not floating — anything stricter would make big machines unplaceable on real terrain.
- Placement asks the other four questions (editable, air, unoccupied, clear of the player) **per cell**, then support **once for the footprint** — `Player.can_place_at`, with `size`/`support_dirs` **defaulted** to a 1×1 that mounts anywhere, which is the block rule unchanged. That default is why every block call site stayed a three-argument call and the 2.7 behaviour is preserved by construction rather than by re-testing.
- **The harvest gate (3.3)** joins it as `facing`/`harvests`, defaulted the same way so 3.1's five-argument call sites are untouched too: a deployable whose scene authors `harvests_deposits` needs **at least one deposit in its harvest block** (§Categories → Miner) or the placement is refused. ❗️**One generic clause, no `Miner` type check anywhere** — the answer is read off the scene through `Player.placement_harvests` / `Deployable.scene_harvests`, so the "no branches in the player" bargain `place_scene` made holds through the first machine that needed a new placement rule. The ghost passes the same two arguments and draws the harvest block as a **second, dimmer outline in the same validity colour**; a 3×2 whose ore block sits three cells away is unreadable without it.

**One drop path.** A removal swing, a mob destroying it (`hp <= 0`) and lost support all converge on `pop_to_pickup()`. **Nothing the player built is ever destroyed outright** — it falls on the floor as a pickup carrying `grants_xp = false` ([progression.md](progression.md): place → remove → place must not be a looting-XP fountain). So a wave that eats your torch line costs you a walk rather than the torches. `pop_to_pickup` is **idempotent** and frees its cells **eagerly**, both for the reasons in [player-combat.md](player-combat.md) §Un-deploying.

**Cargo drops with the machine (3.2).** A `take_cargo()` virtual on the base — empty by default — hands over everything the deployable was *holding*, and `pop_to_pickup` spawns those stacks through the **same sink**, so there is still exactly one drop path and no second exit for items. A conveyor returns its slot; a furnace returns its input and output (there is no fuel slot — §Categories). ❗️**Losing the cargo was a silent item sink**: nothing reports it, and a wave chewing through a loaded line would quietly eat the haul on it. ❗️`take_cargo` is **destructive** (a conveyor drains through its own `extract_item`) rather than a pure read — `pop_to_pickup` re-enters itself through `entity_changed`, so a read-only version would be one re-entry away from duplicating the stack. Cargo carries `grants_xp = false` like the machine itself: ore on a belt already paid XP when it was mined, and belt → pop → re-place must not become a fresh looting-XP loop ([progression.md](progression.md)). An **inserter returns nothing** — its transfer is atomic by design, so there is never a stack on the arm.

The **2.7 torch was a one-cell special case that landed before this base existed** and folded in here at 3.1 — it already registered in the entity dict and was placed/removed through the same player verbs ([terrain.md](terrain.md) §Lighting, [player-combat.md](player-combat.md) §Placement / §Un-deploying). It stays at `scripts/terrain/torch.gd`: this doc owns the *base*, terrain.md owns *that torch as a light source*.

## Support & popping (3.1)
`Automation` connects **one handler to both `Terrain.tile_changed` and `Terrain.entity_changed`** (the `Waves` listener precedent). Mine the tile a torch is mounted on and the torch drops as a pickup instead of hanging in mid-air.

**Cost: O(1) per changed cell.** A deployable is only affected by a tile it *touches* and is registered per occupied cell, so the handler probes exactly **five cells** (`pos` + 4 cardinal neighbours) with `get_entity` and enqueues the hits. `get_entity_cells()` is never called, and world gen costs **zero** because `set_cell_raw` emits no signal at all.

❗️**The queue is a work queue, not a debounce timer, and it is required even at chain depth 1.** A support check is four `is_solid` calls, not a 57 ms field solve ([enemies.md](enemies.md)) — there is nothing to amortize. What needs taming is **re-entrancy**: `pop_to_pickup` calls `remove_entity` per cell, which emits `entity_changed`, which lands straight back in the same handler. So the handler *only enqueues* (array + dedupe dict) and `_process` drains with `while not _queue.is_empty()`. Pops during the drain append to the array being drained — **that append is the cascade**; recursion would blow the stack on a long chain and is never used. Idempotency comes from `pop_to_pickup`'s own flag, so a machine queued through four of its cells still drops one item.

Termination is provable — every step either does nothing or permanently removes one deployable, and only a removal can enqueue more — and a debug-only `assert(guard < MAX_DRAIN_STEPS)` backstops a future predicate that breaks the argument. Coalescing is the dedupe dict: fifty changes around one torch cost one check.

`Automation.reset_run()` clears the queue and is called from `main.gd`'s restart, per tech-design.md's standing convention. ❗️A cell surviving a restart would re-check something else entirely in the new world.

## Categories
- **Miner (3.3)** — `scripts/automation/miner.gd`, **3×2**, directional, `support_dirs = 15`. Every `extract_ticks` (10 = 1 s) it takes `extract_count` reserve **1:1** out of the first deposit cell in its harvest block, row-major, into its **one output slot** — shaped byte-identically to a conveyor's and an `Inventory`'s, so ore moves miner → inserter → belt with no conversion. It is the first thing in the game that produces an item without a click, and the first multi-cell placeable — the thing 3.1's W×H footprint and item-preview ghost existed for.
  - ❗️**"On deposit tiles" means its HARVEST BLOCK, not its footprint.** All five `*_deposit` materials are `is_solid`, and `Terrain.place_entity` rejects a solid cell — the "entity cells are air" invariant is baked into three places in `terrain.gd` (the `place_entity` guard plus two asserts) and two consumers depend on it by name (`Enemy._attackable_entity`, [enemies.md](enemies.md) §Locomotion). **Do not relax `place_entity`.**
  - **The block is the same W×H as the footprint, flush, one span along `facing` — the arrow points AT the ore.** `Deployable.harvest_cells_at(origin, area, facing)`, span = `area.x` horizontally and `area.y` vertically, so a 3×2 reaches 3 cells left/right but only 2 up/down and the block never gaps or overlaps. "Placed on the deposit" is then delivered by **gating placement** on ≥1 harvest cell being a deposit (§Deployable base): the ghost stays red until you stand the miner against ore and rotate to face it. A silent 50/50 like the inserter's behind/front, so it has an all-four-facings test.
  - Ore comes out through `Terrain.extract_reserve` ([terrain.md](terrain.md) §Deposit mining), **not** `damage_tile` — 1:1 into the slot instead of 5-reserve-for-1-drop onto the floor, and it pays no XP on either channel.
  - ❗️**A full output stalls rather than extracting into nothing**, and room is checked against the drop id *before* extracting: the transfer seam has no way to put ore back in the ground, so extracting into a slot that cannot hold it (full, or holding a different ore) would destroy it. Not spending the cooldown on a stalled tick is the inserter's rule, for the inserter's reason.
  - **Idle state.** `is_idle()` — no harvest cell is a deposit — recomputed **per tick** (six `get_material_id` calls at 10 Hz), because a deposit is destroyed to air the moment its reserve hits zero, i.e. *underneath* an otherwise perfectly placed miner. ❗️One state for "ran dry" and "never had one": from the player's side both mean *this machine is producing nothing, come and move it*. Surfaced as the HUD's idle-machine counter ([ui.md](ui.md)), not a toast.
  - `support_dirs = 15` costs nothing at placement — the deposit it stands against is solid — so it only pops if literally every neighbour is dug out, and it never vanishes mid-wave.
  - `accept_item` is left at the base's **refusing** default: a miner is not a chest, so an inserter pointed into one does nothing with no type check anywhere.
- **Conveyor** — non-blocking directional scaffold tube; items levitate through. One slot per tile; slot holds a **stack**. Tiered variants move faster.
- **Inserter** — **mandatory for all *machine* I/O** (locked): picks from the tile behind (`cell - facing`: conveyor/machine output), drops into the tile in front (`cell + facing`: conveyor/machine input), one swing per `swing_ticks` (5 = 0.5 s). **Stacking inserters** (higher tier) move whole stacks per swing. The player's own hand is not a machine — RMB **hand-feeding** (3.2, [player-combat.md](player-combat.md) §Hand-feeding) is deliberately outside this rule.
  - ❗️**A failed insert hands the item BACK to the source, it never drops it.** The inserter extracts before it knows the destination will take it, so a refused or partial transfer returns the remainder through the source's own `accept_item`. Safe *precisely because* of the locked tick order: inserters run **before** conveyors, so the slot it just emptied has not been advanced into and is still free.
  - ❗️**An idle poll does not burn the cooldown.** Spending it on a tick where the source was empty or the destination full would make the inserter feel laggy and make a chain's throughput depend on *when* the source happened to fill. Not picking up is also the whole of back-pressure: the item stays on the source belt and the line jams behind it.
  - **The transfer is atomic — the inserter holds nothing between ticks.** A held item would be a third place an item can live (serialized by 4.3, popped when the inserter is removed, reasoned about in the conveyor tie-break) for a visual a swinging arm already sells. The arm is polish, not state.
  - Behind/front is a silent 50/50 exactly like the support bitmask's Up/Down bit, so it has a dedicated all-four-facings test.
- **Stacker** — conveyor-like; when its output is blocked and the incoming stack matches its held stack's item id, merges them (up to max stack size) — saturated lines densify automatically.
- **Crafting stations (3.3)** — `scripts/automation/crafting_station.gd`, named for the CATEGORY rather than for the furnace: 4.2's assembler and the ammo press are a `.tscn`, a `station_id` and rows in `data/recipe_defs.gd`, **not** a second script. The furnace is **2×2**, non-directional, `support_dirs = 15`. Per tick it selects the first recipe of its station whose inputs are present, accumulates progress, and at `ticks` consumes and outputs. **The ammo press landed at 3.5a**, pulled forward from 4.2 because a turret needs something to eat — same 2×2 authoring, `station_id = "ammo_press"`, bars in and ammo out, and it cost no change to `crafting_station.gd`, which is the bargain being cashed rather than merely claimed.
  - ❗️**Power only — there is no fuel slot.** This doc said both at 3.1 ("furnace: fuel slot" *and* "powered"); the conflict is resolved in favour of the grid, and the fuel-slot wording is struck here and from `take_cargo`'s contract. A furnace is two slots, input and output — **the coal goes in the generator**. ⚠️ The 3.3 consequence (`is_powered()` stubbed `true`, coal with no consumer) is closed as of 3.4 — see §Power.
  - ❗️**`accept_item` routes by ID, because the seam has no port argument.** An item goes into the input slot only when `RecipeDefs.accepts_input(station_id, id)` says some recipe uses it; everything else is refused. Refusing is the load-bearing half — without it an inserter jams the furnace full of dirt **permanently**, since `extract_item` can never reach the input to get it out.
  - ❗️**`extract_item` reaches the OUTPUT only.** If it could reach the input, an inserter would pull the ore straight back out of the machine it had just fed — a chain that is wired correctly and produces nothing.
  - ❗️**Inputs are consumed on COMPLETION, not on start.** Mid-craft removal then has no half-eaten ore for `take_cargo` to lose, and a full output **stalls at full progress** and resumes the instant it is drained — which is back-pressure, and needs no third place for an item to live. `take_cargo` returns both slots.
  - **The recipe table is `data/recipe_defs.gd`** — static and pure, mirroring `data/item_defs.gd` exactly ([progression.md](progression.md) §Recipe tiers owns it). `inputs` is a **map from day one** even though one input slot can only ever match a single-input row: widening the key of a shipped table later is a rewrite of every consumer. 3.6's crafting tab is a UI over this same table.
- **Power (3.4)** — Generator (2×2, burns fuel constantly, radiates a radius and supplies the grid) and Relay (1×1, a larger radius and no supply, so it extends and bridges coverage). Both are §Power's — it owns the radius, the fuel burn and the brownout rule.
- **Defense (3.5a)** — Walls are placeable solid tiles, not deployables ([terrain.md](terrain.md)).
  - **Turret** — 1×1, non-directional (it auto-targets; a facing arrow would be a lie), `power_demand = 0.5` **and** an ammo slot fed by inserter or hand. ❗️**Both**, deliberately: power alone makes it a free kill zone the moment a generator is up, ammo alone divorces defense from the factory, and needing both is what makes `miner → furnace → ammo press → turret` the thing you build. Targets **nearest in range, full stop** — "highest threat" is incoherent here: `ThreatTable` is a *mob's* private list of who to attack, not a targetability score, and a turret has no threat toward a mob it has not shot yet. Selection is a **static, pure** `Turret.pick_target(candidates, from, range_px)` fed by `Waves.enemies()`, so the part that can be wrong in a way a screenshot hides unit-tests with no world. ❗️Its candidate loop is **untyped**: a typed loop variable fails on the *assignment* of a freed instance, before any `is_instance_valid` guard in the body can run.
  - **The projectile is read off the loaded AMMO** (`ItemStats.projectile`), never authored on the turret, so an ammo tier is a `.tres` pair and there is no turret-side tier table ([progression.md](progression.md) §Recipe tiers). Ammo whose stats resolve no projectile fires nothing and is **not** consumed. `extract_item` stays refusing (ammo loaded is spent, not stored — the generator's rule); `take_cargo` returns it when the turret comes down. Fires under the base's `faction`, so threat attribution is free and a turret tanks its own aggro ([enemies.md](enemies.md) §Aggro).
  - ❗️**An idle poll must not burn the cooldown**: it is reset only on a shot that actually happened, so the turret fires on the first tick a mob enters range — the inserter's rule, for the inserter's reason. Otherwise its DPS would depend on when a mob wandered in. A brownout therefore reads as a slower rate of fire, which is `spend_power_tick` working rather than a special case. Out of ammo ⇒ `is_idle()`, joining the HUD counter with no type check.
  - **Spike trap** — contact damage, **unpowered**.
  - ⚠️ **Turret support is authored per variant, not fixed by the category.** The standard turret is `support_dirs = 4` (Down) — a horizontal base under it; a ceiling variant would author `1` (Up). See §Deployable base.
- **Utility** — torch, chest, respawn beacon, climbables (profiles owned by [enemies.md](enemies.md)), the Core (pre-placed, unique, big HP pool).

Full jam list: miner, conveyor ×2 tiers, inserter (+ stacking), stacker, furnace, assembler, generator, relay, chest, spike trap, basic turret, ammo turret, beacon, ladder (+ rope/pole). ~16, mostly data on shared bases.

## The 10 Hz tick (locked: tick-based slots)
One fixed 10 Hz tick in `Automation` advances the whole logistics sim deterministically. No physics. It sits beside the 3.1 support drain in the same `_process` (drain first), behind the house phase gate — an early return on `Game.state`, not `set_process` — and runs in **BUILD_PHASE *and* WAVE_PHASE**: ❗️the factory running *during* the fight is the fantasy ([plan.md](../plan.md)), so this gate is the one thing that could quietly break it. `step_tick()` and `advance(delta)` are both **public**, for the same reason `drain_support_queue()` is: a test drives the clock itself rather than waiting on real frames. The whole tick is one coarse `Perf.begin(&"automation.tick")` section, so the existing readout picks it up with no overlay change.

**Fixed-step accumulator, and it SUBTRACTS the interval — it never resets to zero.** ❗️`terrain.gd`'s `_sweep_accum` takes the other shape (reset, and at most one iteration per frame); that is the exact thing to avoid here, because it both drifts and silently drops ticks on a long frame, and a conveyor line that loses ticks under load is a factory that quietly runs slow. Note this also means no tick boundary is ever exactly representable: `TICK_INTERVAL` is 0.1, which no binary float holds exactly, so "ten ticks per second" is true to within one tick and tests must not sit on the boundary.

❗️**A catch-up clamp (`MAX_CATCH_UP = 3`) is not optional and is not a tuning knob.** Chrome throttles a backgrounded tab hard, so the first `delta` after a tab-out comes back as one enormous value; without the clamp a 30-second tab-out runs 300 ticks inside a single frame and hangs the page. With it the factory **loses that time** — backlog past the clamp is discarded, not paid off over later frames. That is the correct trade (nobody is watching a belt they cannot see), and it only reproduces in a real browser, so it is written down here rather than left to be "fixed" later.

`tick_alpha()` (`_tick_accum / TICK_INTERVAL`, clamped) is the item renderer's **only** input.

**Registration and iteration order.** Three arrays on `Automation` (`_machines`, `_inserters`, `_conveyors`), joined and left through the `Deployable.on_placed()` / `on_removed()` virtuals 3.1 left empty — so nothing in the player or the placement path knows the registries exist. Machines and inserters tick through one `Deployable.on_tick(terrain)` virtual (default `pass`, terrain handed in so the whole sim tests against a fresh world); conveyors do **not**, because their advance is a whole-group two-phase pass rather than a per-node step.

❗️**Iteration order is ROW-MAJOR BY CELL (y, then x), not insertion order, and that is what makes the tick deterministic at all.** Conveyor advance is order-independent by construction, but two inserters pulling from the same conveyor slot are not, and neither is the tie-break when two conveyors face the same cell. Insertion order is reproducible within a session but **not across [save.md](save.md)'s save/load (4.3)**, which restores entities in file order and would silently change tick behaviour — a loaded factory behaving identically *except at merge junctions* is the one place nobody looks. Row-major is derived from the world itself, so any restore order ticks identically and the save file need not preserve an ordering at all; it also makes the debug overlay read in sim order. Kept cheap with an `_order_dirty` flag and one `sort_custom` before the first tick after a placement — a few hundred elements, at human placement rates.

`Automation.reset_run()` zeroes `tick_count` and the accumulator and **clears all three registries**. ❗️That last part is not redundant with `on_removed()`: deployables are children of `Main` and die with the scene reload without ever being popped, so a surviving array would hold freed references into the next run.

**Conveyors:** stacks are the unit of transport everywhere. One slot per belt, shaped **byte-identically to an `Inventory` slot** (`{}` or `{id, count}`), so a stack moves belt → inserter → chest with no conversion anywhere and `Inventory.STACK_SIZE` is the one cap. `Conveyor.advance_all(terrain, belts)` is **static** — the pass is a property of the group, not of any one belt — and runs three sweeps per tick:

0. **Settle** — tick every cooldown down and reset every `_prev_cell` to the belt's own cell. That reset is what makes the render interpolation self-correcting: the commit overwrites it for movers, so a blocked item's lerp is a no-op and an arriving item's lerp runs for exactly one tick.
1. **Mark** — walk the row-major list, memoizing "does this belt vacate this tick?". **Chain compression falls out of the recursion**: a full line all marks in one pass, so the whole chain advances in a single tick rather than only its head.
2. **Commit** — in three separate sweeps: capture every payload, clear every source, *then* write every target. ❗️Not foldable into one. A belt is routinely both a source and a target in the same tick, so writing one move at a time overwrites a stack that has not vacated yet — the dupe-and-loss bug this shape exists to make impossible, invisible until a full line quietly eats an item.

Rules the mark phase settles, all of them worth stating because each has a plausible wrong answer:
- ❗️**A closed loop of full belts ROTATES.** Re-entering a belt already `RESOLVING` answers **true**, and that optimism is *self-fulfilling*, not a guess: a re-entry can only happen on a genuine cycle (the pass never recurses into an empty belt), the commit is simultaneous, so "the cell will be free" is exactly true. Every frame in the cycle unwinds `true`, giving one move and one claim per member. A naive predicate deadlocks the loop instead. `_evaluate` checks the target's cooldown **before** recursing, so a cooled-down member still blocks the loop properly.
- ❗️**The destination claim is taken AFTER the recursion returns, and the "already claimed" test is repeated there.** A two-belt swap claims the very cell its feeder was about to; claiming before the recursion lets the feeder and the cycle both write one slot and silently destroys a stack.
- **Deterministic tie-break:** two belts facing one cell — the row-major-earlier one claims it, the other keeps its stack and retries. Starting the walk at any member of a cycle yields the same move *set* in a different order, and the commit is order-independent, so the memo carries no hidden dependence on where iteration began.
- **A belt facing nothing (or a machine, wall or inserter) JAMS — it never spills.** Items on a belt never fall on the floor. ❗️**Final as of 3.3, and the earlier clause here is struck**: this line used to promise that 3.3 would route a machine input through `accept_item` at that same point, which contradicts §Categories' locked "inserters are mandatory for all machine I/O". The lock wins — a belt facing a furnace jams exactly as it did, and that jam is what the inserter beside it pulls from.
- **A full slot never merges an identical stack**, even though `accept_item` does: belt-to-belt movement is whole-slot, and densifying a saturated line is the **Stacker**'s job.

**Rendering: ONE immediate-mode `ConveyorItemLayer` (`Node2D`, `top_level`), not a pooled sprite + count label.** It walks `Automation`'s row-major conveyor registry, culls to the viewport with the same view-rect derivation the flow-field overlay uses, and per occupied slot draws `Hud.icon_for(id)` at a position lerped between `prev_cell` and the belt's own cell by `tick_alpha()`, plus a `draw_string` count **only above 1** (`draw_string` is the expensive call and most slots carry one item). `Hud.icon_for` is already a cached `AtlasTexture`/`ImageTexture` builder, so block items all draw from the one tileset atlas and batch well.
- ❗️**A pool was rejected, not skipped.** A pool is N `Sprite2D` + N `Label` CanvasItems and a **capacity to get wrong** — precisely the failure already logged against the fixed-32 projectile pool ([player-combat.md](player-combat.md)). One `_draw` over a culled registry has no capacity, no nodes, and reads the sim directly each frame, so it cannot desync from it. This supersedes the pooled-sprite wording that predated the light grid.
- `z_index` sits **between the tilemap (0) and the LightMap (100)**, so items on a belt are lit like everything else rather than glowing in a dark cave. `_process` calls `queue_redraw()` only while the sim holds at least one item; the cull depends on the view rect, so camera motion alone changes the drawn set and a per-frame redraw is required whenever anything is on a belt.
- The interpolation is a **static pure** `item_position(prev_cell, cell, alpha)` with a clamped alpha, unit-tested without a viewport: it is the one part of the renderer that can be wrong in a way a screenshot hides, and a catch-up frame can otherwise fling an item past its destination.

Throughput levers, all data: (a) tiered conveyors advance every N ticks (`ticks_per_move`, set on *receipt*, so a saturated line moves in lockstep — tier 2 is a second `.tres`, not a second script); (b) stacking inserters; (c) the Stacker.

❗️**Conveyors and inserters author `support_dirs = 0`** — they opt out of the support rule entirely. Belts spanning a gap and a closed loop whose top row is two cells off the ground are both normal factory shapes; making them pop would be an unbuildable game. The opt-out already exists in the base for exactly this ("a free-floating machine opts out of the rule"), so this is data, not a new rule.

**Tick order (fixed, save/load depends on it):** `machines craft → inserters transfer → conveyors advance` — a crafted item can leave the same tick.

**The transfer seam** is two virtuals on `Deployable`, both defaulting to refuse: `accept_item(id, count) -> int` (how many it took; a partial accept is legal and the caller keeps the remainder) and `extract_item(max_count) -> Dictionary` (a detached `{id, count}`, already gone from the source; `{}` for nothing). This is the seam every later consumer uses — 3.3's furnace routes them to input/output slots, 3.5's turret accepts ammo, RMB hand-feed is a single `accept_item(id, 1)`. ❗️**The refusing default is the load-bearing part**: it is what lets an inserter point at a torch and do nothing with no type check anywhere, the same rule that keeps the Core un-removable without a special case. **Two virtuals, not three — there is no `peek`**; the inserter extracts before it knows the destination will take it and hands the remainder back through the source's own `accept_item`, which is safe *precisely because* of the locked order above. Belt-to-belt moves deliberately do **not** go through this seam and cannot: simultaneity needs the whole-group snapshot below. That looks like duplication and is not — unifying them reintroduces the dupe bug.

**Debug:** an **F3 debug-menu checkbox row** ("Automation slots") driving a `Node2D` overlay — per belt the facing arrow, a tinted cell when occupied, the slot's `id×count` and the cooldown counter; per inserter the behind→front line and its cooldown; **per machine (3.3)** its footprint box, its slots (`in —` / `out coal×4`, an empty slot shown rather than omitted), its cooldown or craft progress, a **`NO POWER` / `PWR 60%` line (3.4)** for machines that draw — from the same `is_powered()`/`power_ratio()` reads the bolt uses, because "no power" and "stuck cooldown" look identical from the outside — and for a miner the **harvest block outline** plus a red box and `NO ORE` when it is idle. ❗️The machine pass is not polish: before it, this overlay was blind to the only things that *create* items, so "the belt is empty" and "the miner never started" looked identical. It reads machines with `as` casts, exactly as it already reads belts and inserters — pushing a readout API onto every `Deployable` to keep one debug node tidy is the wrong trade. Tick bugs are the top-listed risk in [plan.md](../plan.md), and this is the other half of that mitigation next to the two-phase commit: it makes a jam, a starved junction or a stuck cooldown *visible* rather than inferred. It sits **above** the light map, unlike the item layer, because a debug readout has to stay legible in an unlit cave.

❗️**Not a hotkey, despite how this line read before 3.2.** [ui.md](ui.md) owns overlays and locks "debug overlays own no keybindings of their own"; F4 is the one surviving exception because it needs the cursor to say *where*, which no button can express. The roadmap's "debug slot overlay hotkey" wording was reconciled at 3.2 — the roadmap owns no decisions.

## Power — radius coverage grids (3.4)
Every Generator and Relay emits a radius. Emitters are graph nodes, edges where radii overlap; connected components = **grids**. A machine is powered if inside any emitter radius of a grid. Per tick each grid compares demand vs. fuelled-generator output; machines run at `min(1, supply/demand)` — **brownouts slow, never hard-stop** (better feel, simpler code). Recompute the graph only on place/remove, never per tick.

**Three decisions taken at 3.4, all of them things the earlier wording left open:**
- ❗️**The relay ships** (✂️5 not fired). It costs exactly one class split and the graph code is identical either way — `PowerGrid` sees a disc, and whether that disc also *feeds* the grid is one `power_supply()` return value. What it buys is the reason to build outward: a generator's radius is small (8 tiles), a relay's is large (12) and supplies nothing, so reaching a distant seam is a chain rather than a second generator.
- ❗️**Machines only draw power.** Conveyors and inserters author `power_demand = 0` and run everywhere, free. **This is zero new code**: neither of them ever calls the power gate, so "belts are free" is authoring rather than an exemption in the tick. A belt line that stops dead outside a circle would also make the buffer between two grids unbuildable.
- ❗️**The bolt icon is always on**, red for unpowered and amber for brownout, rather than appearing only while the overlay is up. Same argument that turned the exhausted-miner toast into a persistent HUD count ([ui.md](ui.md)): a machine goes dark while you are somewhere else, and a signal you have to already be looking for is a signal you miss.

**`Deployable.is_powered()` was the seam and landed stubbed at 3.3** — every machine's `on_tick` already early-outed on it, so 3.4 is a real implementation plus the coverage graph and nothing else changed. It is now a real read, and the machine tick gate is `spend_power_tick()` beside it.

**`PowerGrid` (`scripts/automation/power_grid.gd`) is a pure solver over parallel arrays** — centres, radii, component-per-emitter, then supply/demand/ratio per component. It knows nothing about `Deployable`, `Terrain` or the tree, so the part with a wrong answer that looks right unit-tests with no world at all.
- Two emitters share a grid when `centre[i].distance_to(centre[j]) <= radius[i] + radius[j]` — discs touching or overlapping. ❗️**Inclusive at exact tangency**: a relay gets placed at its reach, and a strict `<` would make the intended placement a coin flip on float rounding. Connectivity is BFS over an O(N²) adjacency test rather than union-find — N is dozens of emitters, it runs on place/remove only, and the reachability argument is one anyone can check by reading it. Iterative, like the support drain, so a long relay chain does not depend on stack depth.
- ❗️**World units, no cell stamping.** `grid_of_point(p)` answers against the discs themselves rather than against a rasterised set of powered cells: nothing has to be invalidated when anything moves, a 3×2 half-overlapping a circle has an unambiguous answer, and the overlay draws the same circles the solver reasons about. Radius is authored **in tiles** and multiplied by `TILE` once, at the one place the graph is built.
- Ratio is `1.0` when demand is zero rather than a division by zero: an empty grid is "fully powered" in the only sense that matters — the next machine placed in it runs.

**`Automation` gains a fourth registry** (`_emitters`) and a `_power_dirty` flag, mirroring `_machines`/`_order_dirty` exactly and joined through the same `on_placed()`/`on_removed()` virtuals. `_refresh_power()` runs at the **top of `step_tick()`, before the machine pass**, in its own `Perf.begin(&"automation.power")` section (the one part of the tick whose cost scales with emitters × machines rather than either): rebuild if dirty → `burn_tick()` every emitter → zero and refill supply → **first machine pass accumulates demand** → resolve → **second machine pass stamps the ratio**.
- ❗️**Two machine passes, and they cannot be folded into one.** A grid's ratio is `supply / total demand`, so no machine's ratio exists until every machine on that grid has declared what it draws. Stamping as we go would give the first machine walked 1.0 and the last one a quarter — a factory whose rate depends on row-major order.
- ❗️**Any footprint cell inside a disc powers the whole machine.** Fair for a 3×2 with one corner in the circle; the alternative (its centre only) puts a machine's power on a point the player cannot see, and a visibly half-covered machine that is dead reads as a bug.
- Emitters are sorted row-major before the rebuild. It changes no ratio — it makes component *numbering* derive from the world rather than from placement order, so the overlay's per-grid colours survive [save.md](save.md)'s restore-in-file-order.
- `reset_run()` clears `_emitters` and drops the grid, for the reason it clears the other three: deployables die with the scene reload without ever being popped, and the graph is *derived* from their positions, so a survivor would hand out coverage from generators that are gone.

**The gate lives on the base, so no machine implements the brownout rule.** `power_demand` and `power_radius` are exports; `is_powered()` / `power_ratio()` are reads; `set_power_ratio()` is stamped by `Automation`; and `spend_power_tick()` is the one a machine's `on_tick` calls.
- ❗️**`spend_power_tick()` is STATEFUL — exactly once per tick, from `on_tick` only.** It is a fractional accumulator: each tick banks `ratio`, and the machine acts on the tick that carries the running total past 1.0. At ratio 1.0 that is *exactly* every tick with no float drift; at 0.5 it is five actions in ten ticks.
- ❗️**Why an accumulator on the base and not a scaled cooldown per machine.** One gate every machine reuses unchanged, versus the brownout rule copied into N machines. Every machine's timing also stays in **whole ticks**, so 4.3 serializes an int and 3.3's cooldown/progress tests keep their exact numbers.
- `_power_ratio` defaults to **1.0** deliberately: `_refresh_power` stamps every registered machine before every machine pass, so the default is only ever read by a machine that was never ticked through `Automation` — i.e. a unit test driving `on_tick` by hand. ⚠️ **A suite that drives `Automation.step_tick()` is not such a test** and needs a supply in its fixture; `test_miner.gd` and `test_crafting_station.gd` both did, and both grew a local emitter double at 3.4.
- `scene_power_radius` / `scene_power_demand` join `scene_size`/`scene_harvests` in the probe set, under the same anti-drift contract: read off an authored instance, never a second copy of the number.

**Generator and Relay.** `PowerEmitter` (`power_emitter.gd`) registers the disc and answers `burn_tick()` / `power_supply()`; **`relay.tscn` uses that script directly** (radius 12, no supply, no fuel). `Generator` (`generator.gd`) subclasses it: 2×2, radius 8, `power_output`, `fuel_ids`, `fuel_ticks` (100 = 10 s per coal). Its `accept_item` id-routes fuel into one `_fuel` slot exactly as `CraftingStation.accept_item` routes recipe inputs, `extract_item` stays at the refusing default, and `take_cargo` hands the fuel back.
- ❗️**It burns constantly, not on demand.** [terrain.md](terrain.md) already says so; it is what makes the coal deposit tier mean something, and it is the simplest code. `burn_tick()` runs *before* supply is read, so a generator that runs dry stops powering on that tick rather than one tick late.
- `is_idle()` is true when it is dry, so it joins the HUD's idle count beside a miner over bare rock — the same "come and feed me" signal, and this one stops the whole factory. `_refresh_idle_count()` therefore walks `_emitters` as well as `_machines`.
- **Bootstrap:** a miner needs power, a generator needs coal, and coal comes from mining — so the opening move is hand-mining coal with the pickaxe. That is Factorio's burner phase, and it is fine.

**Not serialized ([save.md](save.md)):** grids are *derived* from emitter positions and rebuilt on load. Generator fuel and burn counter are ordinary entity internal state, already covered there.

UI: coverage circles drawn with the placement ghost + a **dedicated hotkey (`P`) toggling a persistent power overlay anytime** (colour-coded per grid, supply/demand readouts per generator); bolt icon on unpowered and browned-out machines. (Screen inventory owned by [ui.md](ui.md).)

Perf: the narrow world caps factory size; hundreds of conveyors at 10 Hz is nothing, even on web.
