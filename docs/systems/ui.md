# UI

Owner of: all screens, shortcuts, overlays, pause behavior.

## Character screen — one window, three tabs (locked)
Navigable via tab buttons and cycling keys; each tab ALSO has a direct shortcut (`I` inventory, `C` crafting, `K` skill tree) that opens the window on that tab, or switches tab if open:
- **Inventory tab:** grid inventory + hotbar assignment, **equipment panel** (tool, weapon slots, armor/accessory slots), **player stats readout** (HP, mana, move speed, active buff multipliers). Container view opens alongside when interacting with a chest.
- **Crafting tab:** recipes in **category tabs** (Tools & Weapons / Automation / Logistics / Power / Defense / Components…) for findability; filtered by unlocks, greyed when inputs missing (with missing-item highlight); search box if time allows.
- **Skill tree tab:** node graph ([progression.md](progression.md)).

## Bindings (inventory)
Movement `WASD`/arrows · `Space` jump · LMB use (mine, swing, un-deploy) · RMB place (and **hand-feed**, [player-combat.md](player-combat.md)) · `1`–`0` hotbar · **`R` rotate placement** ([automation.md](automation.md) §Facing) · `I`/`C`/`K` character-screen tabs · `Z` zoom · `P` power overlay · `Esc` pause · `F3` debug menu · `F4` spawn mob at cursor. Everything else the debug panel owns is a row, not a key.

## World camera zoom (locked)
`Z` cycles the world camera zoom **1× → 1.5× → 2×** (default **1×**). Affects only the game world; HUD/UI stays native 720p ([tech-design.md](../tech-design.md) display constraint). Implemented on the player camera ([player-combat.md](player-combat.md), Day 1 step 1.6).

## HUD (1.7, locked)
`scenes/ui/hud.tscn` (CanvasLayer + `scripts/ui/hud.gd`), instanced in main.tscn, hidden until `main.gd::_finish_generation()` shows it and hands over the player via `bind_player` (same ownership moment as the LoadingUI toggle). Native 720p, stock Controls, no theme resource. Testability: the HUD takes its `Inventory` via a settable property defaulting to `Items.player_inventory`; formatting and icon lookup are static funcs.
- **Bars (top-left):** HP red, mana blue ProgressBars with a centered "current / max" label, driven by the player's `health_changed` / `mana_changed` signals ([player-combat.md](player-combat.md) HP/mana stub).
- **Hotbar (bottom-center):** 10 slots (Inventory 0–9), key labels 1–9 then 0, item icon + count, selected slot highlighted via `selected_changed`. Icons: the fully-surrounded autotile frame (`TileLayout.LAYOUT[15][0]`) cut as an AtlasTexture from `terrain_tileset.tres` (atlas source id = `Materials.ORDER` index); ids without tile art fall back to a 16×16 `base_color` swatch (gray when unknown).
- **Elevation (top-right):** `Elevation: <row> — <biome name>` — row is the **raw tile row** (`floori(global_position.y / 16)`, not depth-below-surface), biome from `Biomes.BANDS`; label repaints only on row change. Also feeds the game-over stats screen (2.1).
- **Phase label (top-center, 2.1):** big countdown `M:SS` during BUILD_PHASE (from `Game.countdown_tick`), `Wave n — X remaining` during WAVE_PHASE (2.4, refreshed on `Waves.wave_progress_changed` — the count itself is owned by [enemies.md](enemies.md); the label reads `Waves.remaining()` rather than the signal payload, since Waves is an autoload and handles `wave_started` first). Last-`FINAL_WINDOW` seconds: label turns red + scale-pops and a full-screen `PulseOverlay` ColorRect flashes (alpha tween, no shaders — Compatibility-safe). Countdown *presentation* behavior is owned by [plan.md](../plan.md); this section owns the widgets.
- **Wave banner (centered, 2.1):** announce on `wave_started` / `wave_cleared`, hold-then-fade tween. Also carries the **player death/respawn announcement** (2.5, via the player's `died` / `respawned` signals): a run continues through a player death, so it's an announcement rather than an interruption — the real death screen is 4.5.
- **Core HP (under phase label, 2.1):** slim bar, seeded/driven via `bind_core(core)` (mirrors `bind_player`). HUD takes its `Game` via a settable `game` property defaulting to the autoload (test seam).

- **Rejection toast (bottom-centre, above the hotbar, 2.7):** its own `Toast` Label with its own tween — deliberately **not** a reuse of the wave banner, because a rejected click must never blot out a fight. Shorter than the banner (1.2 s hold, 0.4 s fade): a rejection is a nudge, not an announcement. ❗️**It carries a repeat guard, which is not optional** — placement polls input every physics frame, so a held RMB against a buffer zone fires it 60×/second, and without absorbing identical repeats the tween restarts every frame and the toast never fades. It would ship visibly broken. An identical message is absorbed only while one is still on screen; a *different* message interrupts, so a stale rejection never outlives the one that matters.
- ❗️**The HUD is no longer reached only through `main.gd`'s `%HUD`.** `class_name Hud` + `static func show_toast(message)` backed by an `_instance` set in `_ready` and cleared in `_exit_tree` — the same trick as `ProjectilePool.fire`, and for the same reason: the call sites are many and unrelated (buffer-zone placement today; 3.1 adds placement validity and power coverage), and none of them should own a node path. It is **inert with no HUD in the tree**, so headless tests are unaffected.

- **Selected-item name (above the hotbar, 3.3):** the name of what is in hand, driven by the same `selected_changed` / `slot_changed` pair the hotbar itself uses — ❗️**both**, because mining the last of a stack changes what you are holding without the selection moving. An empty slot names **bare hands** rather than going blank: that is genuinely what LMB will swing with, so it is the honest readout rather than a missing one.
- **Cursor inspector (follows the pointer, 3.3):** names whatever is under the cursor. Precedence **mirrors what a click would do**, so the label can never name something other than what you are about to act on: a hotbar slot (the only screen-space case, `id ×count`) → a mob (`Walker — 22/30 HP`) → a deployable → the tile. ❗️**Air reads as nothing at all, not as "Air"** — naming the absence of a tile would put a label on every second pixel of the screen. A deposit carries its remaining ore (`Copper Deposit — 43 ore left`), which is the one number that decides where a miner is worth putting. Polled in `_process` rather than signal-driven, because the thing that changes is the *cursor*, and nothing emits when a mouse moves over a tile. ❗️Near the bottom edge it flips **above** the cursor instead of being clamped down onto it — hovering a hotbar slot is the common case, and a clamped label lands squarely on the slots either side of the one it is naming. Toggled by the F3 row below; the state is a `static var` on `Hud` reached through `set_inspector_enabled`, the same inert-without-a-HUD seam as `show_toast`.
- ❗️**`Hud.item_name(id)` is THE display name for any item or tile id**, and the reason it is not `Items.stats_for(id).display_name`: every plain block resolves to the shared `BLOCK_DEFAULT`, whose name is the literal word "Block", so a hundred materials would all introduce themselves identically. Authored items win; everything else is its own id title-cased, which Godot's `capitalize()` already does (`copper_deposit` → `Copper Deposit`) — so materials need no second name table to drift from `materials.gd`.
- **Idle-machine counter (top-right, under the elevation label, 3.3):** an `%IdleAlert` Label bound to `Automation.idle_machines_changed(count)`, `visible = count > 0`, amber. ❗️**A persistent count, replacing the exhausted-deposit miner *toast* this doc used to route through `Hud.show_toast`.** A miner runs its deposit dry while you are somewhere else entirely — a toast fires at a screen nobody is looking at and is gone by the time you come back, where a count survives being looked away from. It is also one widget for N machines rather than N notifications. What counts as idle is [automation.md](automation.md)'s (`Deployable.is_idle()`, false for everything that is not a machine, so the tally needs no type check); the signal only fires on a **change**, so an unchanged number is not ten repaints a second. HUD takes its `Automation` via a settable property, same test seam as `game`/`waves`/`progression`. ❗️The glyph is ASCII (`[!]`): the bundled Open Sans has no U+26A0, and a missing glyph renders as a blank box — a warning that looks like a bug.
- **XP bar (under the mana bar, 2.6):** slim amber ProgressBar with a centered `Lv N — cur / next` label, measured against the *current* level's cost so it rebases each level-up. Driven by `Progression.xp_changed` and seeded in `_ready` rather than on the first grant, so a run resumed mid-level ([save.md](save.md)) doesn't show an empty bar until something dies. A level-up reuses the wave banner ("Level 3!") instead of growing a screen — it's worth announcing, not worth interrupting a fight for. The upgrade point it grants is deliberately *not* surfaced until there's a skill tree to spend it in (3.7). HUD takes its `Progression` via a settable property, same test seam as `game`/`waves`.

**Debug menu (locked, F3)** — `scripts/debug/debug_menu.gd`, instanced by `main.gd`, hidden by default, runs `PROCESS_MODE_ALWAYS` so it works under the paused game-over screen. **One panel instead of a keybinding per trick**: adding a debug affordance is a row here, not another global key to remember and collide with. Rows: *toggles* flow-field overlay · **automation slots** (3.2) · perf readout (switching it on calls `reset_stats()`, i.e. "measure from here") · **full bright** · **cursor inspector** (3.3 — ❗️the one row that starts **on**, because it is a player-facing readout rather than a debug overlay, and only lives here because this panel is where a toggle belongs); *buttons* skip countdown · clear wave · poke nearest mob · give test loot · **build factory rig** (3.3) · **give item** (dropdown + quantity + Give) · grant XP · kill player.

**Build factory rig (3.3)** carves a flat 30×4 pocket beside the player with a stone floor, lays a two-row `copper_deposit` seam at its right end, and hands over ten each of miner/inserter/conveyor/furnace **plus generator and relay, and a stack of coal (3.4)**, **plus ammo press and turret (3.5a)** — the whole setup for a production chain in one press. The pocket widened from 22 at 3.5a because the chain grew to four machines; the width is asserted against the machines' **authored footprints** rather than restated as a number, so a machine that grows fails a test instead of a browser check. The spike trap deliberately gets no row: an `ItemDefs.STATS` entry earns it a give-item row for free, which is what that dropdown is for. ❗️The power half is not a convenience: with `is_powered()` live, the old kit built a chain that could never run, `STARTING_KIT` hands out no machines at all, and crafting (3.6) does not exist yet. ❗️It exists because **an exported build has no other way in**: a chain needs a deposit, deposits only generate underground, and there is no console in a web build — so the browser check of the tick, which is the one place `MAX_CATCH_UP` and the deposit-exhaustion path are real ([automation.md](automation.md)), was otherwise a twenty-row dig and a coin flip every time. The seam is placed so a miner set against it **facing RIGHT** is valid and facing away is not, which is the placement rule the ghost is trying to teach.

**Full bright (2.7)** simply hides the light map, because with no multiply pass the world renders unlit ([terrain.md](terrain.md) §Lighting) — it is the row that answers "is this dark because of the depth, or because my light is broken", and it is how the itch screenshots get taken. Solving is skipped while hidden, and switching back re-solves whole rather than fading in.

**Give item sits ALONGSIDE give-test-loot, not instead of it.** The loot row is a one-click fixture that deliberately overflows the hotbar for the loot-bag flow; reproducing that through a dropdown is 16 interactions. Two rows, two purposes. The dropdown lists authored items *and* ordinary materials, excluding deposits and bedrock by the same rule the loot row uses — neither is an item, and handing either out puts an unplaceable id in the inventory. The XP row exists because levelling by hand means mining hundreds of blocks; one press is worth more than the first level costs, so it always visibly fires the whole level-up path (stat grant, banner, bar rebase). The loot and kill rows exist as a pair — they're how the death/loot-bag flow ([player-combat.md](player-combat.md)) gets exercised on demand, so the loot deliberately overflows the 10-slot hotbar into the slots a death actually drops.

**The one surviving debug key is F4, spawn mob at cursor** — it needs the pointer to say *where*, which no button can express. `DebugMenu.is_open` is a **static** flag (same no-autoload trick as `Perf`) read by the player: gameplay polls `Input` directly rather than routing through the UI, so without it every click on a debug button would also swing at the world behind the panel.

**Debug overlays** (hidden by default, instanced by `main.gd`, never in a player's way, no keybindings of their own): flow-field heat map ([enemies.md](enemies.md)) · **automation slot overlay** (3.2 — belt occupancy, counts, facings, cooldowns, and since 3.5a a turret's ammo stack, cooldown and whether it has a target at all: a loaded, powered, silent turret is either out of range or reading a broken query, and those look identical from outside; [automation.md](automation.md) owns what it draws, and records that the roadmap's "hotkey" wording lost to this rule) · perf readout (`scripts/debug/perf_overlay.gd`) — frame pacing, flow-field solve cost, and tile-write cost, existing because the browser has no editor profiler and web perf is the never-cut risk in [plan.md](../plan.md). Its headline figure is the **worst frame in a rolling window**, not mean FPS: a periodic hitch is invisible in an average. It also splits the worst frame by whether a cell write happened near it (**dirty** vs **clean**), which is what attributes a hitch to the tile-change path or exonerates it. Toggling it on resets every accumulator — including baselining Terrain's monotonic write counters, since world gen writes ~240k cells before a run starts. Counters live on `Terrain` (`cell_writes`, `cell_write_usec`, `cell_write_peak_usec`), fed by the single `_write_cell`/`_erase_cell` seam so no mutation escapes them. The last two lines are `scripts/debug/perf.gd` (`Perf.begin`/`end` named sections, ranked by **worst single frame** — an average buries a once-a-second spike) and Godot's own `TIME_PROCESS` / `TIME_PHYSICS_PROCESS` peaks. That last pair is the one that matters: when named sections sum to ~15 ms but `TIME_PHYSICS_PROCESS` peaks far above them, the cost is outside every script. **Read those two as rolling windows, not lifetime maxima** — the 67 ms peak this readout once showed was chased as a per-frame physics cost and turned out to be the one-off creation of every tile body when world gen ends ([terrain.md](terrain.md)); during play physics sits at ~1 ms. Physics nodes are therefore not a thing to design around: combat uses ordinary `Area2D` hitboxes ([player-combat.md](player-combat.md)). Sections are frame-bounded via `Engine.get_process_frames()`, so `Perf` needs no autoload slot and cannot be mis-ordered against the code it measures. It also carries a **light line (2.7)**: the grid region (`cols×rows` and cell count) plus total draw calls. ❗️Deliberately **no light count** — the per-tile grid costs the same whether one torch is lit or a hundred, so a count would be a number that never moves; what actually moves is the region, which scales with zoom, and [terrain.md](terrain.md)'s fallback ladder is written in exactly those terms.

## Other screens
Pause menu · **power overlay** on its own hotkey, togglable anytime ([automation.md](automation.md)) · debug overlay (slot occupancy, fortification score) · death & game-over screens · main menu with seed input (stretch: seedless "New Run" only). Keyboard + mouse only. Toasts for rejected placements (buffer zone — the light cap that used to share this line was deleted with the light grid, [terrain.md](terrain.md)).

**Power overlay (3.4, `scripts/automation/power_overlay.gd`)** — a world-space `Node2D` instanced by `main.gd` beside the other overlays, above the light map so it stays legible in an unlit cave. Two layers with different rules:
- ❗️**The bolt layer is always on and behind no toggle.** A two-triangle lightning bolt over every machine that draws power and is *not* running at full rate — **red** when unpowered, **amber** when browned out — and nothing at all over a healthy one, because an icon on every machine forever is a screen you stop reading. A machine goes dark while you are somewhere else entirely, so this is the same argument that turned the exhausted-miner toast into a persistent count: a signal you have to already be looking for is a signal you miss. ❗️It is **drawn geometry, not a font glyph** — the bundled Open Sans has no U+26A1 and a missing glyph renders as a blank box, exactly the trap the idle counter's `[!]` already paid for.
- **The circles are the toggled half.** Each emitter's disc filled dim and outlined, **coloured by its grid** rather than by the emitter (two generators that merged read as one colour — the whole question the overlay answers), plus a `supply/demand` and burn-state `draw_string` over each generator. Toggled by **`P`** (`toggle_power_overlay`), and toggled through an *internal flag rather than `visible`*, precisely so the bolts survive it.
- The same circles also appear, without the readouts, **while a power-relevant item is in hand** — a furnace as much as a generator, because "will this land powered" is the question you are asking while you look for somewhere to put it. Driven off the same `selected_changed`/`slot_changed` pair as the hotbar, through new `Player.placement_power_radius` / `placement_power_demand` statics (the `placement_harvests` idiom).
- The **prospective** circle of the thing being placed belongs to the placement ghost ([player-combat.md](player-combat.md) §Placement), not here — one owner per meaning, so existing coverage and your-coverage-to-be cannot drift into drawing contradicting circles.

❗️**`P` is the sanctioned exception to "debug overlays own no keybindings", and the rule is otherwise unchanged.** This is a *player-facing* readout, not a debug overlay — the same distinction that lets the cursor inspector be an F3 row that starts on. The bindings list above and [automation.md](automation.md) both already locked `P` for it. The automation **slot** overlay next door stays an F3 row, and F4 remains the one surviving debug key.

❗️**There is no "placement mode" screen, and that is deliberate (3.1).** The placement ghost is not a screen and has no mode to enter: it is world-space drawing on the mining cursor, on whenever the selected item is placeable and off when it is not ([player-combat.md](player-combat.md) §Placement). Nothing here owns it.

## Pause (locked)
`SceneTree.paused` + `process_mode`: gameplay pauses; the pause menu stays **fully interactive** (resume, settings, save during build phase, quit). Forbidden while paused: *gameplay* actions — placing/removing deployables, inventory/crafting manipulation, skill-tree spending. Enforcement: opening pause closes gameplay screens; gameplay input handlers live under paused `process_mode`.
